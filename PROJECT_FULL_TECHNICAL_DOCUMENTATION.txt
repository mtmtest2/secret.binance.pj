1. PROJECT OVERVIEW
================================================================================

--------------------------------------------------------------------------------
1.1 What the system does
--------------------------------------------------------------------------------

This is a single-process, fully asynchronous algorithmic trading system that
trades Binance USDT-margined perpetual futures on the 5-minute timeframe.

It performs, in one process:

  1. Discovery and screening of the tradeable symbol universe directly from the
     Binance futures API (no hard-coded coin list is used once the operator has
     made a selection).
  2. Ingestion of 5m OHLCV candles, L2 order-book snapshots, funding rate, open
     interest, long/short positioning ratios and (where exposed) liquidation
     flow.
  3. A quality-control gatekeeper with targeted auto-healing that re-fetches only
     damaged timestamp ranges and refuses to pass unhealable data downstream.
  4. Causal feature engineering producing a fixed 53-column feature matrix,
     including KAMA, Fractal Dimension Index, rolling-refit GARCH(1,1)
     volatility, a rolling-refit Gaussian HMM regime filter, micro-structure and
     session features.
  5. Forward-looking, risk-tiered triple-barrier label generation producing five
     direction classes plus per-model regression targets.
  6. Training of four independent gradient-boosted models (LightGBM by default,
     XGBoost optional): Direction, Entry, Exit and Risk.
  7. Stateless inference of those four heads on the newest closed candle.
  8. A deterministic, non-ML, 10-rule decision cascade (the "Decision Engine")
     that is the only producer of a TradeSignal.
  9. Execution through one of two interchangeable engines - a live Binance
     executor or a paper trader - plus an event-driven backtester.
 10. A stateful Risk Guard (GREEN/YELLOW/RED) that latches to SQLite and can
     flatten the book.
 11. A batched audit engine that records every decision, including every
     NO_TRADE, with the exact rule that fired.
 12. A FastAPI web panel on port 8000 that drives the whole lifecycle: pick
     pairs, watch setup, arm paper, go live, kill switch.

The system does NOT trade automatically at boot. Trading is armed only by an
explicit operator action (panel button or POST /api/trading/start), unless
AUTOSTART_PAPER_TRADING is set to true.

--------------------------------------------------------------------------------
1.2 Design philosophy encoded in the source
--------------------------------------------------------------------------------

Several invariants are enforced structurally rather than by convention. These are
worth stating up front because they explain many code choices:

  * Causality is a hard rule in Module B. Every transform uses only data at or
    before bar t. GARCH emits the one-step-ahead forecast; the HMM uses a forward
    (alpha) filter, never Viterbi/forward-backward smoothing; micro-structure
    joins are merge_asof(direction="backward").

  * Narrow-waist schemas. Module C talks to Module D only through
    ModelInferenceResult. Module D talks to Module E only through TradeSignal.
    Both are frozen Pydantic models with validators, so leverage > 10,
    probabilities outside [0,1], or a long whose stop sits above its entry are
    structurally impossible to transmit.

  * Explicit degradation. Every ML head has a documented heuristic fallback that
    stamps source=HEURISTIC. Rule R9 refuses to let a heuristic place a live
    order.

  * Never invent data. A symbol whose candles cannot be healed is skipped for the
    cycle. There is no interpolation anywhere in the ingestion path.

  * Pessimism in simulation. The labeler, paper trader and backtester all break
    ambiguous ties against the trade (stop assumed hit before target; liquidation
    checked before stop; stop checked before take-profit).

  * The audit log records rejections. A NO_TRADE row carries the full feature
    snapshot, all four model outputs and the single rule that short-circuited the
    cascade.

1.5 The two exchange connections
--------------------------------------------------------------------------------

[CODE] BinanceDataFetcher takes a `role` parameter: "market_data" or "execution".

  role="market_data"
      Constructed in TradingSystem.__init__ (main.py:93).
      No apiKey / secret is placed in the ccxt config at all
      (fetcher.py:133-135 only sets credentials when role == "execution").
      set_sandbox_mode() is never called for this role, so it is always Binance
      MAINNET. This client supplies every candle, order book, funding rate and
      ticker for training, backtesting, paper trading AND live trading.

  role="execution"
      Constructed by LiveExecutor.__init__ (executor.py:90-92) and, transiently,
      by TradingSystem.verify_credentials (main.py:861).
      Carries EXCHANGE__API_KEY / EXCHANGE__API_SECRET.
      Honours EXCHANGE__TESTNET via exchange.set_sandbox_mode(True).

[DERIVED] Consequences:
  * EXCHANGE__TESTNET affects order routing only. Market data is never testnet.
  * PaperTrader never constructs an execution-role client, so paper trading
    requires no API keys whatsoever.
  * A bug confined to the data path cannot reach the account, because the data
    client has no credentials attached.

[CODE] Both roles restrict ccxt market loading to linear markets only
(fetcher.py:149-166, `_restrict_to_linear_markets`). Two option shapes are
handled because the ccxt option changed from a bare list (4.2) to a dict with a
"types" key (4.5). The comment states the additional motive: in sandbox mode the
spot leg is served by testnet.binance.vision, a different testnet, which would
break startup for reasons unrelated to futures.

1.6 Execution lifecycle / state machine
--------------------------------------------------------------------------------

[CODE] module_f_panel/setup_state.py defines SystemPhase:

   STARTING
       |
       |-- no universe saved --> AWAITING_UNIVERSE --(operator ticks pairs)--+
       |                                                                     |
       v                                                                     |
   COLLECTING_DATA  <----------------------------------------------------------+
       |
       v
   TRAINING ---> READY --(operator arms)--> PAPER_TRADING  <==>  LIVE_TRADING
                   ^                              |
                   +--------(operator stops)------+

   SETUP_FAILED is terminal until the operator retries.

Phase helper properties (setup_state.py:46-59):
   is_trading        -> PAPER_TRADING or LIVE_TRADING
   is_busy           -> COLLECTING_DATA or TRAINING

[DERIVED] Trading can only be armed from READY (or while already trading).
COLLECTING_DATA / TRAINING / AWAITING_UNIVERSE / SETUP_FAILED all refuse.

1.7 Concurrency model
--------------------------------------------------------------------------------

Everything runs on ONE asyncio event loop.

Long-lived tasks:
  * "web-server"       - uvicorn.Server.serve()                     (main.py:991)
  * "shutdown-watch"   - waits on the shutdown asyncio.Event        (main.py:992)
  * "setup-pipeline"   - the background setup coroutine             (main.py:250)
  * "audit-writer"     - AuditEngine flush loop (2s interval)       (audit_engine.py:132)
  * "position-monitor" - LiveExecutor monitor loop (5s default)     (executor.py:129)
  * "paper-monitor"    - PaperTrader monitor loop (5s default)      (paper_trader.py:84)
  * APScheduler AsyncIOScheduler job "trading_cycle" (5m cron)      (main.py:945)

CPU-bound work is pushed off the loop:
  * FeatureService.build -> asyncio.to_thread (default) or a ProcessPoolExecutor
    when use_process_pool=True (features.py:973-1000). Note: main.py always
    constructs FeatureService(settings) with the default use_process_pool=False,
    so the process pool is never used in the running system.
  * TradeLabeler.generate -> asyncio.to_thread (processor.py:178)
  * MLSubsystem.infer -> asyncio.to_thread (ml_models.py:1041)
  * BaseModelHead.train -> asyncio.to_thread (ml_models.py:998)
  * Backtester._simulate -> asyncio.to_thread (backtester.py:171)

Bounded concurrency:
  * BinanceDataFetcher._semaphore   = exchange.max_concurrent_requests (default 8)
  * DataPipeline._symbol_semaphore  = exchange.max_concurrent_requests
  * FeatureService._semaphore       = features.max_feature_workers (default 4)
  * MLSubsystem._inference_semaphore= ml.inference_workers * 2 (default 4)

Mutual exclusion:
  * TradingSystem._cycle_lock  - non-blocking check; an overrunning cycle causes
    the next slot to be SKIPPED, not queued (main.py:546-548).
  * TradingSystem._setup_lock  - serialises setup runs.
  * RiskGuard._lock            - guards all state mutation.
  * LiveExecutor._lock / PaperTrader._lock - guard the positions dict.

  Binance REST (mainnet, public)
        |
        | fetch_ohlcv / fetch_order_book / fetch_funding_rate /

        |                            re-validates (up to qc.max_heal_attempts)
        v
  DatabaseHandler.upsert_candles / upsert_order_book / upsert_futures_metrics
        |                            (INSERT ... ON CONFLICT DO UPDATE)
        v
  MarketDataBundle  (symbol, candles, book, futures, QCReport)
        |
        v
  DatasetProcessor
        |-- training path:  load_ohlcv_dataframe + futures frame + book frame
        |                   -> FeatureService.build -> TradeLabeler.generate
        |                   -> pooled, sorted by (timestamp, symbol), NaN-dropped
        |                   -> ProcessedDataset (features, 4 target sets, metadata)
        |
        `-- inference path: same loads, FeatureService.build only, take the LAST
                            fully-formed row -> InferencePayload
        |
        v
  MLSubsystem.infer_many -> per symbol: DirectionPrediction, EntryPrediction,
        |                   ExitParameters, RiskAllocation -> ModelInferenceResult
        v
  DecisionEngine.evaluate_many -> ranked by confidence, R0..R9 cascade
        |                          -> DecisionResult (+ TradeSignal on EXECUTE)
        v
  PaperTrader.execute  or  LiveExecutor.execute  -> ExecutionReport / Position
        |                                            -> trades table
        v
  AuditEngine.log_decision (EVERY decision) -> asyncio.Queue -> batched
        |                                       insert into audit_logs
        v
  FastAPI panel reads audit_logs / trades / equity_curve / status snapshot

  The orchestrator. Owns one instance of every component, drives the 5-minute
  decision cycle, hosts the web server, implements the SystemController protocol

WHEN EXECUTED
  It is the process entry point. `python main.py [command]`.

async startup()                                               (main.py:169-236)
  Ordered initialisation. Deliberately network-tolerant.
    1. Logs a banner naming the data source (always MAINNET public) and the
       execution environment (MAINNET or TESTNET) plus whether credentials are
       configured (masked).
    2. await database.initialize()      - creates engine, PRAGMAs, schema
    3. await audit.start()              - starts the audit writer task
    4. await risk_guard.load()          - restores a persisted RED latch
    5. try: await fetcher.load_markets(); market_data_ready = True
       except QuantSystemError: records market_data_error and logs a five-line
       block telling the operator to run
       `curl -s https://fapi.binance.com/fapi/v1/ping`.
       [CODE] Reaching Binance is explicitly NOT a precondition for booting; the
       panel must come up so the operator can see why it failed.
    6. self.ml.load_all() - loads whichever of the four .joblib artifacts exist.
       Missing heads are logged, not fatal.
    7. self.active_symbols = await universe.get_selection()
    8. risk_guard.register_halt_callback(self.engine.emergency_flatten)
    9. try: await engine.start()
       except QuantSystemError: a live engine refusing to start (bad or missing
       credentials) causes a fallback to paper - trading_mode is set to "paper",
       a new PaperTrader is built, its emergency_flatten is registered, started.
       [NOTE] register_halt_callback APPENDS. On this fallback path two callbacks
       are registered: the dead LiveExecutor's and the new PaperTrader's.
   10. If risk_guard.is_halted, logs CRITICAL that no trades will occur until a
       manual reset.

async _setup_collect(symbols)                                 (main.py:310-345)
  Stage 1. phase = COLLECTING_DATA. progress.begin/advance.
  Calls pipeline.bootstrap_history(symbols, progress=report) where `report` is a
  closure updating SetupProgress so the panel's progress bar moves per symbol.
  Then, for each symbol, database.candle_count(symbol); symbols with >= 500
  stored candles are "usable".

    * If SOME are unusable -> logs a warning naming them.

async start_trading(mode) -> dict                             (main.py:408-453)
  Refusal ladder (each raises ValueError, surfaced by the panel as HTTP 409):
    1. mode not in {"paper","live"}
    2. not self.phase.can_arm_trading  ("setup must finish first")
    3. self.risk_guard.is_halted        ("reset it before trading")
    4. mode == "live" and not self.ml.all_loaded
       -> "live trading requires all four trained models; heuristic fallbacks
           are blocked"
    5. mode == "live": awaits verify_credentials() and refuses if not valid.
       The comment states why a non-empty key check is insufficient: a wrong
       secret, a spot-only key and an IP-allow-list miss are indistinguishable
       until a signed request is attempted.
    6. not self.active_symbols -> "no universe selected"
  If mode != current trading_mode, calls _switch_engine(mode).
  Then trading_enabled = True, phase = PAPER_TRADING or LIVE_TRADING, logs a
  WARNING, writes an audit event rule="OPERATOR_ARM".

async stop_trading(flatten=False) -> dict                     (main.py:455-480)

  written. Default behaviour deliberately leaves open positions being managed to
  their own TP/SL - "pulling the strategy does not mean abandoning live risk".

async _switch_engine(mode)                                    (main.py:482-495)

async trading_cycle() -> dict                                 (main.py:539-577)
  The scheduled entry point.
    * If _cycle_lock.locked(): logs a warning and returns {"skipped": True}.
      Overlapping cycles are impossible; a long cycle causes the next slot to be
      skipped rather than queued.
    * Generates a cycle_id (uuid4), records the start time.

async _run_cycle(cycle_id) -> dict                            (main.py:579-677)
  The A -> F pipeline for one bar.
    1. If not self.active_symbols -> {"skipped": "no universe"}.
    2. MODULE A: bundles = await pipeline.run_cycle(active_symbols).
       last_cycle_symbols_ok = len(bundles).
       If empty -> audit event rule="QC_ALL_FAILED", return.
    3. GATE: if not phase.is_trading or not trading_enabled -> logs "Data
       refreshed ... trading is disarmed" and RETURNS.
       [CODE] This is deliberate: ingestion runs whenever a universe exists so
       arming paper trading takes effect on the very next bar. But it also means
       that while disarmed there are NO feature computations, NO inferences, NO
       decisions and therefore NO audit rows other than the QC/system events.
    4. account = await _account_state(); state = await
       risk_guard.update_equity(account.equity).
    5. MODULE B: payloads = await processor.build_inference_payloads(list(bundles)).
       If empty -> audit event rule="FEATURES_COLD", return.
    6. MODULE C: inferences = await ml.infer_many(list(payloads.values())).
    7. MODULE D: builds a DecisionContext:
           risk_guard_state = state.value
           trading_enabled  = self.trading_enabled and risk_guard.can_trade
           trading_mode     = self.trading_mode
           open_positions   = len(engine.positions)
           open_symbols     = engine.open_symbols
           equity           = account.equity
           size_multiplier  = risk_guard.size_multiplier
       decisions = decisions.evaluate_many(list(inferences.values()), context)
    8. MODULE E + F: for each decision, if is_executable -> _execute(decision);
       then ALWAYS audit.log_decision(decision, cycle_id, state.value,
       execution_detail).
    9. _record_equity(); logs a one-line cycle summary; returns a dict.

  _LOG_FORMAT = "%(asctime)s | %(levelname)-8s | %(name)-34s | %(message)s"

  class RingBufferHandler(logging.Handler)
      Keeps the last `capacity` records as dicts {timestamp, level, logger,
      message} in a collections.deque(maxlen=capacity). emit() is wrapped in a
      bare try/except calling self.handleError - "a logging handler must never
      raise". snapshot(limit) returns the newest `limit` records, most recent
      first.

  LOG_BUFFER - a module-level singleton RingBufferHandler. This is what
  GET /api/logs serves, which is why the panel can show a live log without
  touching the filesystem.

  configure_logging(level, log_dir)
      Guarded by a module-level _CONFIGURED flag so it runs exactly once.
      Removes all existing root handlers, then installs:
        * StreamHandler(sys.stdout)
        * LOG_BUFFER
        * RotatingFileHandler(log_dir/"quant_system.log", maxBytes=25 MB,
          backupCount=5, encoding="utf-8") when log_dir is not None
      Finally forces WARNING level on the noisy third-party loggers:
      ccxt, urllib3, asyncio, apscheduler.executors.default, aiosqlite.

  get_logger(name) -> logging.getLogger(name)

      via expected_timestamps() and returns every grid point not present. Returns
      [] for blocks shorter than 2 rows.

  CHECK FAMILY 2 - _check_price_logic
      Per candle, in short-circuit order:
        non-finite (NaN/inf) in o/h/l/c or volume -> NAN_VALUES (CRITICAL)
        any price <= 0                            -> NON_POSITIVE_PRICE (CRITICAL)
        high < low, high < max(o,c), low > min(o,c) -> PRICE_LOGIC_VIOLATION
      All three are healable.
      [NOTE] These invariants are already enforced by the Pydantic model, so
      reaching this layer implies the data arrived through a different,
      unvalidated path. The docstring says so, and the checks are kept as
      CRITICAL anyway.

  CHECK FAMILY 3 - _check_volume_logic
      NEGATIVE_VOLUME       CRITICAL, healable
      EXCESSIVE_ZERO_VOLUME CRITICAL, healable - fires only when the block has at
                            least min_rows_for_statistics rows and the zero-
                            volume share exceeds max_zero_volume_ratio
      VOLUME_SPIKE          WARNING, NOT healable - volume above
                            median(positive volumes) * volume_spike_median_multiple

  CHECK FAMILY 4 - _check_return_outliers
      Skipped entirely below min_rows_for_statistics rows, and skipped when any
      close is <= 0 (already reported by the price check).
      log_returns = diff(log(closes)); simple = expm1(log_returns).
        HARD screen: |simple| > qc.max_abs_candle_return
              -> RETURN_OUTLIER CRITICAL, healable
        SOFT screen: |log_ret - median| / (1.4826 * MAD) > return_mad_zscore_limit
              -> RETURN_OUTLIER WARNING, not healable
              soft_mask &= ~hard_mask so a bar is never reported twice.
      Skipped when MAD == 0.
      The docstring gives the reason for MAD over standard deviation: "a single
      40% glitch print inflates sigma enough to hide itself, whereas the MAD has
      a 50% breakdown point".
      Offending timestamps are candles[index + 1] because a return at index i
      belongs to the bar that closed it.

  _check_freshness
      lag_bars = (last_closed_candle_open_ms() - newest_stored) // timeframe_ms
        lag <= 0                 -> no issue
        lag > qc.max_lag_bars    -> STALE_DATA CRITICAL, healable

      attached to a CRITICAL issue. If that set is non-empty, the window is
      [min - one bar, max + one bar] so boundary candles are refreshed too.
      If it is empty but candles exist, the window is the whole block.

3.5.2  module_b_features/indicators.py                             (264 lines)

PURPOSE
  Every indicator implemented from first principles on NumPy/pandas. The
  docstring states the motive: ta-lib requires a compiled C extension, a poor fit
  for a portable VPS. Two non-negotiable properties are declared:
    * Causality  - the value at t uses only indices <= t. No center=True, no
                   backward fill, no shift(-k).
    * Determinism- bit-for-bit reproducible, which is what makes backtest results
                   comparable to live ones.

  true_range(high, low, close)
      Wilder's TR = max(high-low, |high-prev_close|, |low-prev_close|), computed
      by concatenating the three series and taking a row-wise max with
      skipna=False (so the first bar is NaN, not a partial max).

  wilder_smooth(series, window)
      ewm(alpha=1/window, adjust=False, min_periods=window).mean()

  atr(high, low, close, window) = wilder_smooth(true_range(...), window)

  rsi(close, window)
      Wilder-smoothed average gain / average loss.
      Guards: avg_loss replaced by NaN at 0 before dividing; the result is then
      forced to 100 where avg_loss <= 0 and to 0 where avg_gain <= 0; finally
      clipped to [0, 100]. This avoids inf.

  kama(close, window=10, fast=2, slow=30)
      Kaufman's Adaptive Moving Average.
          ER_t   = |close_t - close_{t-n}| / sum(|close_i - close_{i-1}|)
          SC_t   = (ER_t * (2/(fast+1) - 2/(slow+1)) + 2/(slow+1))**2
          KAMA_t = KAMA_{t-1} + SC_t * (close_t - KAMA_{t-1})
      The volatility term is a rolling sum of |price changes|; the direction term
      is |values - roll(values, window)| with the first `window` entries NaN'd.
      efficiency_ratio is nan_to_num'd and clipped to [0,1].
      Seeded with the simple mean of the first window+1 closes at index `window`,
      then a single O(n) Python loop for the recursion (the docstring notes this
      is much faster than rolling.apply).
      Returns all-NaN when size <= window.
      Purpose per the docstring: in a clean trend ER -> 1 and KAMA tracks price;
      in chop ER -> 0 and KAMA flattens, which is the noise filter the direction
      model needs.

  fractal_dimension_index(close, window=30)
      Within each rolling window: min-max normalise the closes to [0,1],
      accumulate the path length on a grid whose vertical step is the normalised
      price change and horizontal step is 1/n, then
          FDI = 1 + (ln(path_length) + ln(2)) / ln(2n)
      Implemented with np.lib.stride_tricks.sliding_window_view so the whole
      series is a handful of vectorised operations.
      A perfectly flat window (span <= 0) is assigned 1.5 (treated as a random
      walk). Result nan_to_num'd (nan->1.5, +inf->2.0, -inf->1.0) and clipped to
      [1,2]. Output is written at offset window-1.
      Interpretation given in the docstring: ~1.0 straight trend, ~1.5 random
      walk, ~2.0 violent chop. The README states verification results of 1.25 for
      a straight line and 1.99 for an alternating series.

  adx(high, low, close, window=14) -> (adx, plus_di, minus_di)
      Standard Wilder directional movement:
          +DM where up_move > down_move and up_move > 0
          -DM where down_move > up_move and down_move > 0
          +DI = 100 * wilder_smooth(+DM) / ATR   (ATR zeros -> NaN first)
          DX  = 100 * |+DI - -DI| / (+DI + -DI)
          ADX = wilder_smooth(DX.fillna(0))

  bollinger(close, window=20, num_std=2.0) -> (middle, width_pct, position)
      middle   = rolling mean
      dev      = rolling std(ddof=0)
      width    = (upper-lower)/middle, NaN-filled to 0
      position = %b = (close - lower)/(upper - lower), clipped to [-1, 2]

  rolling_percentile_rank(series, window)
      series.rolling(window, min_periods=max(5, window//10)).rank(pct=True).
      The docstring calls this "the workhorse that turns non-stationary
      quantities into stationary features a gradient-boosted tree can generalise
      from", and notes Rolling.rank ranks the LAST element of each window, which
      is what makes it causal by construction.

  rolling_zscore(series, window)   - trailing (x-mean)/std, zero-variance guarded,
                                     NaN-filled to 0.
  realized_volatility(log_returns, window) - rolling std(ddof=0),
                                     min_periods=max(5, window//2).
  slope(series, window)            - series.diff(window) / |series|, i.e. a
                                     price-relative slope so the value is
                                     comparable across BTC and PEPE.

  _rolling_garch_forecast(log_returns) -> pd.Series
      window = min(garch_window, max(100, size//2)). If size < window+5 it
      immediately returns _ewma_volatility.
      `arch` is imported LAZILY; ImportError degrades to EWMA with a warning.
      Returns are scaled by 100 for numerical conditioning.
      For each index from `window` to the end:
          needs_refit = (not fitted) or ((index - window) % garch_refit_every == 0)
          on refit: sample = scaled[index-window+1 : index+1]; _fit_garch(...)
              -> updates omega, alpha, beta, mu, sigma2 (last conditional
                 variance) and held_forecast (the model's own 1-step forecast)
          if GARCH(1,1) (the configured default):
              residual = scaled[index] - mu
              sigma2_{t+1} = omega + alpha*residual^2 + beta*sigma2_t
              output[index] = sqrt(sigma2_{t+1}) / 100
              sigma2 = sigma2_{t+1}
          else (p or q != 1):
              output[index] = sqrt(held_forecast) / 100  - the last refit's
              forecast is HELD until the next refit ("still causal, just less
              responsive")
      If the output is entirely NaN, falls back to EWMA.
      [CODE] The key causality claim: the value written at t is the one-step-
      ahead forecast for t+1, computed from information available at t.

  _fit_garch(arch_model, sample, p, q) -> dict | None
      Returns None (so the caller keeps the previous fit) when: sample < 50 rows;
      std(sample) <= 0; the optimiser raises; or the parameters are degenerate
      (omega <= 0, alpha < 0, beta < 0, or alpha+beta >= 1 i.e. non-stationary).
      Model: arch_model(mean="Constant", vol="GARCH", dist="normal",
      rescale=False), fit(disp="off", maxiter=200), warnings suppressed.
      Extracts omega, alpha[1], beta[1], mu; last_variance from
      conditional_volatility[-1]**2; forecast_variance from
      result.forecast(horizon=1, reindex=False).variance, with a manual GARCH
      recursion fallback for older arch releases.

      installed (lazy import, warning logged).

          on refit: _fit_hmm on the trailing window; then the forward filter is
              RE-SEEDED over the entire fitting window so alpha reflects
              everything known at `index` and nothing more.
          between refits: standardise the single new point with the refit's
              scaler, compute the diagonal Gaussian log-density, then
              alpha_log = log_matmul(alpha_log, log_transmat) + emission,
              normalised by subtracting log_sum_exp.

          state_map, renormalised, and argmax gives hmm_regime.

3.5.4  module_b_features/labeler.py                                (619 lines)

PURPOSE
  "The ONLY place in the system that is allowed to look into the future, because
  it manufactures the ground truth used for supervised training. It must
  therefore never be applied to the live-inference path - the processor enforces
  that."

  Three conservative modelling choices are stated in the docstring:
    1. Worst-case intra-candle ordering. When a single candle touches both
       barriers, the STOP is assumed hit first. "Any other assumption
       manufactures phantom winners."
    2. Barrier fills, not close fills. A resolved trade exits exactly at its
       barrier price; only expired trades mark to the horizon close.
    3. Heat is measured. The maximum adverse excursion is recorded as a fraction
       of the stop distance and drives the risk tier.

  _CHUNK_ROWS = 20_000 - rows per vectorised chunk, bounding peak memory at
  O(chunk * horizon).

  generate(frame) -> pd.DataFrame

      max_holding_bars + 1 rows (InsufficientDataError otherwise).
      Computes barrier distances, simulates BOTH sides, derives the volatility
      percentile, classifies, and attaches per-model targets.
      Adds these columns:

          long_outcome, short_outcome, long_mae_ratio, short_mae_ratio,
          long_mfe_ratio, short_mfe_ratio, long_pnl_pct, short_pnl_pct,

          target_risk_score, selected_side, selected_mae_ratio

      `horizon` rows that cannot be simulated. Logs the label distribution over
      valid rows.

  _barrier_distances(frame, close) -> (tp_distance, sl_distance)
      Volatility scale precedence:
          1. ATR where finite and > 0
          2. garch_volatility * close (converting a return to a price distance)
          3. close * 0.0025 (a 0.25% floor, "a sane floor for liquid 5m perps")
      tp_distance = scale * tp_atr_multiple  (default 2.0)
      sl_distance = max(scale * sl_atr_multiple, close * 1e-5)  (default 1.0)
      Both are known at bar t, so barrier placement introduces no look-ahead.

  _simulate(high, low, close, tp_d, sl_d, horizon, is_long) -> _SideSimulation
      Chunked driver; simulatable = rows - horizon.

  _simulate_chunk(...)
      Forward windows: row i sees bars i+1 .. i+horizon, built with
      sliding_window_view over high[chunk_start+1 : chunk_end+horizon].
      For a LONG:
          tp_price = entry + tp_dist;  sl_price = entry - sl_dist
          tp_touched = future_high >= tp_price
          sl_touched = future_low  <= sl_price
          running_adverse   = minimum.accumulate(future_low)
          running_favorable = maximum.accumulate(future_high)
      For a SHORT the roles mirror exactly.
      first_tp / first_sl = argmax of the boolean masks (first True index).
      THE TIE-BREAK:
          stop_first   = sl_any & (~tp_any | (first_sl <= first_tp))
          target_first = tp_any & ~stop_first
      i.e. when both are touched on the same candle, the stop wins.
      exit_index = first_sl / first_tp / horizon-1 (expiry).
      outcome defaults to EXPIRED and is overwritten by STOP_LOSS / TAKE_PROFIT.
      exit_price = sl_price / tp_price / close at chunk_start+horizon (the
      horizon close), and pnl_pct is signed by direction.
      Exit-model targets:
          horizon_favorable = running_favorable[:, -1]  (the best price anywhere
                              in the horizon)
          peak_index        = argmax(future_high) for long / argmin(future_low)
                              for short
          heat_to_peak      = entry - running_adverse[peak_index]  (long)
          optimal_tp        = (horizon_favorable - entry)/entry * 0.9
                              ("leave room for slippage")
          optimal_sl        = (heat_to_peak / entry) * 1.15, floored at
                              0.5 * sl_dist / entry
                              (a stop tighter than half the volatility-scaled
                              distance "sits inside ordinary 5m noise")
          optimal_trailing  = optimal_tp * 0.5
      Written back:
          mae_ratio    = clip(adverse_move / sl_dist, 0, 2)
          mfe_ratio    = favorable_move / tp_dist
          bars_to_exit = exit_index + 1

  _volatility_percentile(frame)
      Uses garch_vol_rank if present, else atr_rank, else a constant 0.5.
      NaNs become 0.5.

  _classify(long_side, short_side, volatility_percentile)
      Row-by-row Python loop. Selection rules:
          1. UNRESOLVED (the tail)          -> NO_TRADE_OR_FAIL / tier NONE
          2. A side qualifies only when its TAKE_PROFIT resolved the trade.
          3. Both qualify (a whipsaw that ran both ways) -> the side that
             resolved FIRST wins; ties broken by the LOWER mae_ratio.
          4. Neither qualifies              -> NO_TRADE_OR_FAIL / tier NONE
          5. Tier from the winner's mae_ratio, escalated by volatility.
             VERY_HIGH collapses to NO_TRADE_OR_FAIL when discard_very_high_risk
             is set (the default) - "a trade that only worked because the market
             was violent is not an edge worth learning". The tier column still
             records VERY_HIGH.
          6. tier in {LOW, MEDIUM} -> *_SUCCESS_LOW_RISK
             tier == HIGH          -> *_SUCCESS_HIGH_RISK
      Also fills `chosen` with +1 (long), -1 (short) or 0.

  _risk_tier(mae_ratio, volatility_percentile) -> str
      Base tier from MAE ratio:
          <= low_risk_mae_ratio    (0.35) -> 0 LOW
          <= medium_risk_mae_ratio (0.60) -> 1 MEDIUM
          <= high_risk_mae_ratio   (0.85) -> 2 HIGH
          otherwise                        -> 3 VERY_HIGH
      Non-finite MAE -> VERY_HIGH immediately.
      Volatility escalation:
          percentile >= extreme_volatility_percentile (0.95) -> forced to 3
          percentile >= high_volatility_percentile    (0.80) -> +1, capped at 3
      Rationale: "the same heat is far more dangerous when the next candle can be
      three times as large".

  _attach_model_targets(...)
      entry_quality (Entry model, binary):
          1.0 only when a side was selected AND its mae_ratio <=
          low_risk_mae_ratio. "That is precisely the 'enter now vs wait one
          candle' question the model must answer."
      target_tp_pct / target_sl_pct / target_trailing_pct (Exit model,
          regression): copied from the WINNING side's optimal_* arrays; NaN on
          rows with no selected side.
      target_risk_score (Risk model, regression, in [0,1]):
          heat_component       = 1 - clip(mae_ratio, 0, 1)
          volatility_component = 1 - clip(volatility_percentile, 0, 1)
          raw                  = heat_component * (0.5 + 0.5*volatility_component)
          Written only where a side was selected; 0.0 elsewhere.

      The safety rails that make ANY regressor output tradeable:
        1. If atr_pct > 0: sl = max(sl, atr_pct * 0.5)
        2. sl = clamp(sl, 0.0015, 0.0800)
        3. tp = clamp(tp, 0.0020, 0.1500)
        4. tp = clamp(tp, sl*1.1, sl*6.0)     <- enforces 1.1 <= R:R <= 6.0
        5. tp = min(tp, 0.1500)

CLASS RiskModel (name = "risk_model")               - MODEL 4
  PREDICTS: an opportunity score in [0,1] (a regressor on the labeler's
  target_risk_score), which DETERMINISTIC logic then converts into an integer
  leverage and a capital allocation.

  train(dataset)
      Plain purged split, _make_regressor(), eval_metric="l2".
      Metrics: mae and r2.

  predict(features, direction_confidence, risk_tier="UNKNOWN") -> RiskAllocation
      score = model.predict(aligned)[0] clamped to [0,1], or _heuristic_score.
      HARD VETOES (both return leverage=0 with an abort_reason):
        1. garch_vol_rank >= decision.max_volatility_percentile (0.97)
        2. direction_confidence < decision.min_direction_confidence (0.70)
      SIZING:
        confidence_span   = 1 - min_direction_confidence          (0.30)
        confidence_factor = clamp((conf - 0.70) / 0.30, 0, 1)
        volatility_factor = 1 - clamp(garch_vol_rank, 0, 1)**2
        tier_factor       = {"LOW":1.0, "MEDIUM":0.75, "HIGH":0.5}.get(tier, 0.6)
        composite = score * (0.35 + 0.65*confidence_factor)
                          * volatility_factor * tier_factor
        leverage_cap = min(decision.max_leverage, risk.max_leverage)   (10)
        leverage     = floor(composite * leverage_cap)
        if leverage < decision.min_leverage (1) -> ABORT with
           "sized leverage 0x below the minimum 1x (composite=...)"
        allocation = min_alloc + (max_alloc - min_alloc) * composite
                   = 0.01 + 0.19 * composite, clamped to [0.01, 0.20]
      [DERIVED] composite must reach 0.10 for leverage to be 1x. Since composite
      is a product of four factors each <= 1, and tier_factor is at most 1.0
      while (0.35 + 0.65*confidence_factor) is at most 1.0, this requires a
      genuinely strong score. This is the single most restrictive numeric gate in
      the system after R1.

  _heuristic_score(row, direction_confidence) -> float
      0.4*direction_confidence + 0.3*clamp(adx/50, 0, 1) + 0.2*fdi_trending

      Polls fetch_order every 2 s until limit_order_timeout_seconds. Returns as
      soon as the status is "closed" or "filled". On timeout: cancels the order
      (critical=False), and if a PARTIAL fill exists returns that order;
      otherwise raises ExecutionError "limit order expired unfilled".
      "Chasing the rest with a market order at a worse price is how a small edge
      becomes a negative one."

  _place_protective_orders(position)
      Two reduce-only orders with params {"reduceOnly": True,
      "workingType": "MARK_PRICE"}:
          TAKE_PROFIT_MARKET with stopPrice = take_profit
          STOP_MARKET        with stopPrice = stop_loss
      Both prices rounded with price_to_precision; the returned ids are stored in
      exchange_order_ids.
      MARK_PRICE rationale: "matches how Binance evaluates liquidation, so the
      stop cannot be triggered by a last-price wick that never touched the mark".

  _monitor_loop()
      Every position_monitor_interval_seconds (5 s): if positions exist, batch
      prices, then per position update_excursions(price, price) and
      _maybe_advance_trailing. Every reconcile_interval_seconds (60 s) also calls
      reconcile(). CancelledError re-raised; any other Exception logged with a
      traceback and the loop continues - "the monitor must never die".
      [NOTE] update_excursions(price, price) passes the same value as both high
      and low, so the live executor's MAE/MFE only ever sees polled prices, never
      intra-poll extremes.

  _maybe_advance_trailing(position, price)
      new_stop = position.advance_trailing(price); returns if None.
      Cancels the OLD stop order first (critical=False, failures warned), then
      places a fresh STOP_MARKET at the rounded new level and stores the new id.
      "The cancel is done first: briefly having no stop is safer than briefly
      having TWO, which would double-close the position."
      If the replacement fails, logs CRITICAL and calls _market_close(...,
      MANUAL, note="stop replacement failed").

  reconcile()
      fetch_positions (critical=False; a failure just skips this round).
      Builds the set of symbols the exchange reports with non-zero contracts.
      An exchange position we do NOT track is logged as a warning ("not managed
      by this engine") and otherwise ignored.
      Anything WE track that the exchange no longer reports is passed to
      _book_external_close.

  _book_external_close(position)
      Attempts to determine which protective order fired by fetching the TP order
      then the SL order and checking for a closed/filled status. Defaults to
      STOP_LOSS at the effective stop; upgrades to TAKE_PROFIT or TRAILING_STOP
      (when trailing was active) and uses the order's average/price as the exit.
      Then _finalise and _cancel_symbol_orders.
      [NOTE] Liquidation is never inferred here; an exchange-side liquidation
      would be booked as STOP_LOSS at the effective stop price, which understates
      the loss relative to what actually happened.

  close_position(symbol, reason=MANUAL) - under the lock, delegates to
      _market_close, or returns "no open position".

  _market_close(position, reason, note="")
      Cancels all resting orders on the symbol, sends a reduce-only market order,
      reads the average price (falling back to a ticker, then to entry_price),
      and calls _finalise. A failed close logs CRITICAL "MARKET CLOSE FAILED" and
      returns a rejected report - the position REMAINS in _positions.

  _finalise(position, exit_price, reason, note="")
      gross      = (exit - entry) * quantity * direction
      exit_fee   = exit * quantity * taker_fee
      fees_paid += exit_fee
      realized_pnl = gross - fees_paid - funding_paid
      Sets exit_price, closed_at, close_reason ("REASON" or "REASON:note"),
      status (LIQUIDATED only when the reason is LIQUIDATION).
      Removes the position, persists the close, then
      await risk.record_trade_result(realized_pnl, symbol).
      [NOTE] fees_paid already includes the ENTRY fee, so realized_pnl is net of
      both legs. Funding is subtracted but the live executor never accrues any
      (see below).
      [NOTE] The live executor has NO funding accrual logic at all. There is no
      counterpart to PaperTrader._accrue_funding, so position.funding_paid is
      always 0.0 in live mode and the realised PnL recorded in the trades table
      omits funding costs that the exchange did actually charge.

  _cancel_symbol_orders / cancel_all_orders - best-effort cancel_all_orders per
      symbol, warnings only.

  emergency_flatten(reason) - the Risk Guard halt callback. Logs CRITICAL,
      cancels everything, then market-closes every position inside a per-symbol
      try/except - "one symbol that refuses to close must not leave the remaining
      positions open". Logs how many positions remain afterwards.

  _persist_open / _persist_close - insert, then update-or-insert on close. Both
      wrapped in a blanket except - "DB must not break trading".

  _extract_fee(order, price, quantity) - reads order["fee"]["cost"], then sums
      order["fees"][*]["cost"], and finally estimates price*quantity*0.0005.
      [NOTE] The 0.0005 fallback is hard-coded rather than read from
      execution.taker_fee.

3.7.5  module_e_execution/paper_trader.py                          (555 lines)

PURPOSE
  "The live executor with the network calls intercepted." It mirrors
  LiveExecutor's public surface exactly (start, execute, close_position,
  emergency_flatten, fetch_account_state, positions, open_symbols, stop,
  reconcile, cancel_all_orders), so the orchestrator swaps engines without a
  single conditional.
  What it explicitly does NOT do is pretend simulation is free: fees, slippage,
  funding, liquidation and conservative barrier ordering are all modelled.

CLASS PaperTrader (mode = "paper")

  __init__ - _balance seeded from execution.paper_starting_balance; _last_prices
      cache; lock; monitor task handle.

  start() - _restore_state() (reloads the virtual balance from
      system_state["paper_trader_state"]), then starts the "paper-monitor" task.
  stop()  - cancels the monitor and persists the balance.

  fetch_account_state()
      Fetches live prices for open symbols, then:
          unrealized  = sum(unrealized_pnl(price) - funding_paid)
          used_margin = sum(margin)
          equity      = _balance + unrealized
      [NOTE] Unrealised PnL is reduced by funding_paid here AND funding_paid is
      subtracted again in _close when the position is booked. Between those two
      points the accounting is consistent (equity is marked, then realised), but
      the entry fee is deducted from _balance immediately at open while the exit
      fee is only applied at close.

  _prices(symbols) - fetch_tickers, updating _last_prices; on failure logs,
      reports an API error to the Risk Guard, and serves the cached prices.

  execute(signal) -> ExecutionReport
      Same guards as the live executor (KillSwitchEngaged on RED, daily cap,
      already-open symbol). Then under the lock:
          margin = signal.margin_for(equity); rejects when margin <= 0 or
          margin > account.free_margin
          market_price = live ticker (falling back to signal.reference_price)
          fill_price   = _apply_slippage(market_price, action, is_entry=True)
          quantity     = (margin * leverage) / fill_price
          Position.from_signal(...)
          fees_paid    = fill_price * quantity * _entry_fee_rate()
          _balance    -= fees_paid          (the entry fee realises immediately,
                                             exactly as on the exchange)
      Logs a "[PAPER] OPEN ..." line showing the slippage-adjusted fill and the
      price it slipped from.

  _apply_slippage(price, action, is_entry)
      buying = (action is LONG) == is_entry
      Buying pushes the price UP by slippage_bps, selling pushes it DOWN.
      "Entering long and exiting short both buy, so both are penalised upward."

  _entry_fee_rate() - taker_fee for market orders, maker_fee for limit orders.

  _monitor_loop() - every position_monitor_interval_seconds, mark_to_market().

  mark_to_market()
      Under the lock, for every position with a positive price:
          update_excursions(price, price)
          _accrue_funding(position, price, now_ms)
          if _hit_liquidation      -> close at liquidation_price, LIQUIDATION
          advance_trailing(price)
          if _hit_stop(effective_stop) -> close at that stop,
                                      TRAILING_STOP if trailing_active else
                                      STOP_LOSS
          if _hit_take_profit      -> close at take_profit, TAKE_PROFIT
      "Barrier precedence is deliberately pessimistic: liquidation, then stop,
      then take-profit. A tick that could plausibly have hit more than one always
      books the worse outcome."

  _hit_liquidation / _hit_stop / _hit_take_profit - simple directional
      comparisons against the polled price.

  _accrue_funding(position, price, now_ms)
      Charges once per funding_interval_hours (8 h) measured from
      last_funding_ms, using the most recent funding rate Module A recorded for
      the symbol:
          payment = quantity * price * rate * direction
          funding_paid += payment
      "Longs pay shorts when the funding rate is positive, which is the normal
      state of a bull market and a real, compounding cost of carry."
      [NOTE] The interval is measured from position open, not from the exchange's
      00:00/08:00/16:00 UTC settlement boundaries. The backtester, by contrast,
      DOES use the real boundaries (timestamp % interval_ms == 0). The two
      engines therefore charge funding at different moments.

  _latest_funding_rate(symbol) - reads the newest futures_metrics row; 0.0 on any
      failure or empty frame.

  close_position(symbol, reason=MANUAL) - fetches a price and calls _close.

  _close(position, raw_exit_price, reason)
      Liquidations get NO slippage relief - "the position is wiped at the
      liquidation price and the entire margin is lost, which is what actually
      happens on the exchange".
          exit_price = raw price for liquidation, else slippage-adjusted
          gross      = (exit - entry) * quantity * direction
          exit_fee   = exit * quantity * taker_fee
          fees_paid += exit_fee
          net        = gross - exit_fee - funding_paid
          if LIQUIDATION: net = max(net, -margin)
          realized_pnl = net
          _balance += gross - exit_fee - funding_paid
          if LIQUIDATION: _balance = max(_balance, 0.0)
      [NOTE] The reported realized_pnl is clamped at -margin for a liquidation,
      but the BALANCE update on the line below adds the UNCLAMPED
      `gross - exit_fee - funding_paid`. On a liquidation whose gross loss
      exceeds the committed margin, the trades table and the virtual balance
      disagree, and the balance is reduced by more than the isolated margin the
      position should have risked. The subsequent max(_balance, 0.0) only
      prevents a negative balance, not the over-charge.
      Then removes the position, persists, and awaits
      risk.record_trade_result(realized_pnl, symbol).

  cancel_all_orders() - a no-op, "kept for interface parity".
  reconcile()         - re-prices the virtual book (mark_to_market).
  emergency_flatten(reason) - closes every virtual position with reason
      KILL_SWITCH, per-symbol try/except, then persists the balance.

  _persist_open / _persist_close / record_equity_point / _persist_state /
  _restore_state - as for the live executor, plus:
      record_equity_point() computes the drawdown against risk.peak_equity and
      appends an equity_curve row. This is what main._record_equity calls for the
      paper engine.

3.7.6  module_e_execution/backtester.py                            (664 lines)

PURPOSE
  "Realism is the whole point of this file. A backtester that is easy to make
  profitable is worthless, so every shortcut that flatters results has been
  closed."
  The five closed shortcuts, verbatim from the docstring:
    * Signals fill on the NEXT bar's open, never on the close that produced them.
    * Worst-case intra-candle ordering (adverse barrier always books first).
    * Full cost model: taker fees both legs, slippage on every market fill,
      funding at the real 00:00/08:00/16:00 UTC boundaries.
    * Isolated-margin liquidation checked on every bar.
    * The same concurrent-position cap and one-position-per-symbol rule as live.

  It also states the justification for precomputing features once per symbol:
  "That is exactly equivalent to computing them bar by bar - and safe - BECAUSE
  every transform in Module B is causal; the property is verified there rather
  than assumed here."

  _BARS_PER_YEAR = 365*24*12 = 105,120 (the Sharpe/Sortino annualisation factor)

DATACLASS BacktestReport (slots)
  start, end, initial_equity, final_equity, trades, equity_curve, metrics,
  symbols, signals_generated, signals_rejected.
  summary() - a 20-line fixed-width text report.
  to_dict() - JSON view truncated to the last 500 trades and 2000 curve points.

CLASS Backtester (mode = "backtest")

  run(symbols, max_candles, initial_equity, warmup_bars) -> BacktestReport
      _prepare (async) then _simulate via asyncio.to_thread.

  _prepare(symbols, depth) -> dict[str, DataFrame]
      Per symbol: load candles (skipped below 200 rows), load the futures frame,
      build features, drop rows with any NaN in FEATURE_COLUMNS.
      [CODE] order_book is passed as None ALWAYS:
          self._features.build(ohlcv, futures if not futures.empty else None,
                               None)
      [NOTE] Training features (via DatasetProcessor) DO include the order-book
      join. The backtester's features therefore have ob_imbalance = 0,
      ob_imbalance_delta = 0, ob_spread_bps = 0 and ob_spread_rank = 0.5 for
      every bar, while the model was fitted on rows where those columns carried
      real values wherever snapshots existed. This is a train/backtest feature
      distribution mismatch. See 13.6.

  _simulate(featured, funding, initial_equity, warmup_bars) -> BacktestReport
      Builds a merged, sorted timeline of every distinct timestamp across all
      symbols, optionally skipping `warmup_bars` from the front.
      Indexes each symbol's frame as {timestamp: row}.
      Then, per timestamp, four ordered phases:

      PHASE 1 - resolve barriers on open positions using THIS bar
          _accrue_funding, then _resolve_bar; on a resolution, _book_close adds
          the balance delta and the trade row is appended.

      PHASE 2 - fill signals raised on the PREVIOUS bar
          "A signal is good for exactly one bar: if it cannot be filled on the
          very next open it is dropped rather than chased at a worse price."
          Skips when the symbol has no row this bar, already has a position, or
          the concurrent cap is reached. _fill returns a Position; the entry fee
          is deducted immediately. `pending` is then cleared unconditionally.

      PHASE 3 - generate new signals from THIS bar's close
          Builds a DecisionContext with risk_guard_state="GREEN",
          trading_enabled=True, trading_mode="backtest", the live open-position
          set, the marked equity and size_multiplier=1.0.
          [DERIVED] The Risk Guard is NOT simulated in the backtest. Drawdown
          halts, losing-streak throttling, YELLOW sizing and the daily trade cap
          have no effect on backtest results.
          [DERIVED] trading_mode="backtest" means R9 never blocks heuristic
          fallbacks, so a backtest run with missing artifacts silently evaluates
          the heuristics instead of failing.
          Iterates symbols in dict order (not confidence order, unlike
          evaluate_many), breaking once len(positions)+len(pending) reaches the
          cap. Counts generated and rejected.

      PHASE 4 - mark to market
          equity = balance + unrealized; update the running peak; append a curve
          point {timestamp, equity, balance, drawdown_pct, open_positions}.
          Breaks out of the whole loop when equity <= 0 ("Account wiped out").

      After the loop every still-open position is force-closed at the final bar's
      close with reason SHUTDOWN.

  _decide(symbol, row, context) -> DecisionResult
      Builds a one-row feature frame from the 53 columns, an InferencePayload
      with a 6-key snapshot, then ml.infer_sync + decisions.evaluate.
      [NOTE] The backtest snapshot omits ob_imbalance, which the audit engine
      records; irrelevant here since the backtester does not write audit rows.

  _fill(signal, row, equity) -> Position | None
      fill_price = bar OPEN, pushed against the trade by slippage_bps.
      margin = signal.margin_for(equity); rejected when <= 0 or > equity.
      quantity = margin * leverage / fill_price.
      Then RE-ANCHORS the barriers to the actual fill:
          LONG:  tp = fill*(1+tp_pct), sl = fill*(1-sl_pct),
                 trailing_trigger = fill*(1 + tp_pct*0.5)
          SHORT: the mirror image
      [NOTE] The trailing trigger is re-derived as HALF THE TAKE-PROFIT DISTANCE,
      not from signal.trailing_trigger (which the Decision Engine derived from
      exit_params.trailing_activation_pct, itself clamped to [tp*0.25, tp*0.95]).
      The backtester therefore arms trailing at a different point than the live
      and paper engines do for the same signal. See 13.6.
      Entry fee = fill * quantity * taker_fee; last_funding_ms = the bar
      timestamp.

  _resolve_bar(position, row) -> (CloseReason, price) | None
      update_excursions(high, low) - the backtester is the only engine that sees
      genuine intra-bar extremes.
      For a LONG: adverse_level = max(effective_stop, liquidation_price); the
      HIGHER of the two is reached first on the way down, so that level wins.
      adverse_hit = low <= adverse_level; target_hit = high >= take_profit.
      For a SHORT the mirror, with a liquidation > 0 guard.
      If adverse_hit: decides liquidation vs stop by which level is nearer the
      adverse direction, and returns TRAILING_STOP when trailing was active.
      Else if target_hit: TAKE_PROFIT.
      Else: the trail may ratchet on this bar's FAVOURABLE extreme, and the bar's
      ADVERSE extreme is then RE-TESTED against the tightened stop -
      "a bar that ran up and then gave it all back would otherwise escape until
      the next bar, an optimism that compounds across a backtest".

  _accrue_funding(position, row, rates, timestamp)
      Only when timestamp % (funding_interval_hours * 3600000) == 0, and not more
      than once per interval. Uses the exact recorded rate for that timestamp or
      _nearest_rate (the most recent at or before it).

  _book_close(position, raw_price, reason, timestamp) -> float
      Slippage on non-liquidation exits, taker exit fee, delta = gross -
      exit_fee - funding_paid, clamped at -margin for a liquidation. Returns the
      balance delta (the entry fee was already deducted at fill time).

  _unrealized(positions, indexed, timestamp) - marks to this bar's close, minus
      funding_paid.

  _compute_metrics(report) -> 21 metrics
      total_trades, winning_trades, losing_trades, win_rate,
      profit_factor (gross_profit / gross_loss; math.inf when there are wins and
      no losses), expectancy, average_win, average_loss, largest_win,
      largest_loss, gross_profit, gross_loss, net_profit, total_return_pct,
      annualised_return_pct, max_drawdown_pct, sharpe_ratio, sortino_ratio,
      calmar_ratio, total_fees, total_funding, liquidations.
      years = number of curve points / _BARS_PER_YEAR.
      _max_drawdown - running peak, guarded against non-positive peaks.
      _period_returns - simple per-bar equity returns, non-finite dropped.
      _sharpe  = mean/std(ddof=1) * sqrt(105120), 0 when fewer than 2 returns.
      _sortino = mean / sqrt(mean(downside^2)) * sqrt(105120).

4.3 Automated setup pipeline
--------------------------------------------------------------------------------

  run_setup(force_retrain) - under _setup_lock

  STEP 0  If trading is armed, stop_trading() first.

  STEP 1  symbols = universe.get_selection()
          EMPTY -> phase = AWAITING_UNIVERSE, progress reports "Pick the
          perpetual futures pairs to trade in the web panel", log the panel URL,
          RETURN. The system now waits indefinitely for the operator.

          The operator opens http://<ip>:8000/universe:
            GET /api/universe/available
              -> UniverseManager.discover()
                   load_markets (ccxt cached)
                   fetch_raw_tickers (ONE unfiltered fetch_tickers call, filtered
                                      locally, via the INTERACTIVE call path so a
                                      blocked upstream fails in ~15-30 s rather
                                      than minutes)
                   filter to active linear USDT-settled perpetual swaps
                   per symbol: merge market metadata with the ticker, compute
                     spread_bps, effective_min_notional, amount_step,
                     granularity_usdt, listed_days
                   run the four screens, record a reason per failure
                   normalise and weight the four score components
                   sort by (eligible, score) descending
                   memoise for 900 s
            Optionally GET /api/universe/suggest -> the top target_count eligible
            symbols, which the page pre-ticks.
            POST /api/universe/select {symbols, start_setup: true}
              -> authorise() (no-op when WEB__API_TOKEN is blank)
              -> UniverseManager.save_selection: validates every symbol against
                 the discovered market list, warns on (but accepts) ineligible
                 explicit choices, computes `changed`, persists
                 system_state["universe_selection"]
              -> main.save_universe writes an audit event and calls
                 launch_setup(force_retrain=changed)

  STEP 2  _setup_collect(symbols)  ->  phase = COLLECTING_DATA
          pipeline.bootstrap_history(symbols, progress=report)
            per symbol, under the semaphore:
              newest = latest stored timestamp
              start  = max(end - 6000*300000, newest + 300000)
              if start > end: nothing to do
              fetch_ohlcv_range -> paginated forward walk, deduplicated by
                                   timestamp
              validate_candles; if it fails, validate_and_heal (targeted
                                   re-fetch, merge, re-validate, up to 4 rounds
                                   with exponential backoff)
              upsert_candles (ON CONFLICT DO UPDATE)
            The progress callback moves the panel's bar per completed symbol.
          Then candle_count per symbol; symbols with >= 500 stored candles are
          "usable". Zero usable symbols raises. Some unusable symbols only warns.

  STEP 3  _setup_train(symbols, force_retrain)  ->  phase = TRAINING
          Skips entirely when auto_train is off and force_retrain is false.
          Skips when all four artifacts are loaded AND the universe is unchanged
          AND force_retrain is false.
          Otherwise:
            dataset = processor.build_training_dataset(symbols)
              per symbol (SEQUENTIALLY):
                load_ohlcv_dataframe(limit=6000)
                load_futures_metrics_frame(limit=6000)
                _load_order_book_frame(limit=6000)
                FeatureService.build -> to_thread(FeatureEngineer.build)
                  price -> volatility -> volume -> GARCH -> HMM ->
                  micro-structure -> session
                to_thread(TradeLabeler.generate)
                  barrier distances -> long simulation -> short simulation ->
                  volatility percentile -> classify -> per-model targets
                add a `symbol` column
              pooled = concat(...).sort_values(["timestamp","symbol"])
              _to_dataset: keep label_is_valid rows, inf -> NaN, dropna over the
                53 features + label + target_risk_score, split into the four
                target families
            An empty dataset raises QuantSystemError.
            ml.train_all(dataset)  - four heads in order direction, entry, exit,
              risk; each fitted on a worker thread and immediately saved to
              artifacts/models/<name>.joblib. Per-head failures are recorded, not
              raised.
            Any head reporting an error raises QuantSystemError, which the
            wrapper turns into phase = SETUP_FAILED.
            On success: system_state["trained_universe"] = {symbols, trained_ms,
            rows}.

  STEP 4  phase = READY. Banner: "Arm paper trading from the panel or POST
          /api/trading/start". If autostart_paper_trading is true,
          start_trading("paper") is called here.

--------------------------------------------------------------------------------
4.4 The 5-minute trading cycle, step by step
--------------------------------------------------------------------------------

  The APScheduler cron fires at HH:M0:10 / HH:M5:10 UTC.

  trading_cycle()
    * If _cycle_lock is already held: log a warning, return {"skipped": True}.
      An overrunning cycle causes the NEXT slot to be dropped.
    * cycle_id = uuid4()

  _run_cycle(cycle_id):

  ---- A. INGESTION + QC ----------------------------------------------------
  If active_symbols is empty -> return {"skipped": "no universe"}.

  pipeline.run_cycle(active_symbols)
      asyncio.gather over _process_symbol, each under the semaphore:
        gather(fetch_ohlcv, fetch_order_book, fetch_futures_metrics,
               return_exceptions=True)
            fetch_ohlcv        -> 500 closed 5m candles, the forming bar dropped
            fetch_order_book   -> top 20 levels reduced to spread/imbalance/
                                  microprice over 10 levels; None on an
                                  empty/crossed book
            fetch_futures_metrics -> six sub-fetches gathered, each degrading to
                                  a neutral default on failure
        An OHLCV exception drops the symbol for this cycle.
        validate_and_heal(symbol, candles, _refetch)
            timestamp integrity / price logic / volume logic / MAD return
            outliers / freshness
            on CRITICAL + healable: sleep(backoff), re-fetch ONLY the damaged
            window (padded one bar each side), merge over the corrupt rows,
            re-validate; up to qc.max_heal_attempts (4)
            unhealable or exhausted -> DataIntegrityError -> the symbol is
            SKIPPED for the cycle. Never interpolated.
        Non-fatal book/futures issues are folded into an enriched QCReport.
        upsert_candles, upsert_order_book, upsert_futures_metrics.
      Returns only bundles where is_valid is True.

  last_cycle_symbols_ok = len(bundles).
  No bundles -> audit system event QC_ALL_FAILED, return.

  ---- GATE ------------------------------------------------------------------
  if not phase.is_trading or not trading_enabled:
      log "Data refreshed for N symbol(s); trading is disarmed", RETURN.
  [DERIVED] While disarmed, the cycle is an ingestion-only warm-keeping loop.

  ---- EQUITY + RISK GUARD ---------------------------------------------------
  account = engine.fetch_account_state()
      PaperTrader: live tickers -> equity = virtual balance + unrealised
      LiveExecutor: fetch_balance + marks -> equity = USDT total + unrealised
      Any exception -> a degraded AccountState from risk_guard.current_equity
      AND a record_api_error.
  state = risk_guard.update_equity(account.equity)
      rolls the UTC day if needed, updates peak equity, evaluates RED then YELLOW

  ---- B. FEATURES -----------------------------------------------------------
  processor.build_inference_payloads(list(bundles))
      per symbol, concurrently:
        load 1220 candles + futures + order-book frames from SQLite
        FeatureService.build on a worker thread -> the 53-column matrix
        drop rows with any NaN in the feature columns
        STALENESS GUARD: the newest complete row must be the newest raw row,
          otherwise the symbol is skipped
        -> InferencePayload(symbol, timestamp, close, 1-row features, snapshot)
  No payloads -> audit system event FEATURES_COLD, return.

  ---- C. INFERENCE ----------------------------------------------------------
  ml.infer_many(payloads)
      per symbol, on a worker thread, under a semaphore:
        direction = DirectionModel.predict(features)
        entry     = EntryModel.predict(features, action=direction.action)
        exit      = ExitModel.predict(features)          -> _assemble rails
        risk      = RiskModel.predict(features, direction.confidence,
                                      direction.implied_risk_tier)
        -> ModelInferenceResult with latency_ms and model_versions
      Per-symbol failures are logged and omitted.

  ---- D. DECISIONS ----------------------------------------------------------
  context = DecisionContext(
      risk_guard_state = state.value,
      trading_enabled  = trading_enabled AND risk_guard.can_trade,
      trading_mode     = trading_mode,
      open_positions   = len(engine.positions),
      open_symbols     = engine.open_symbols,
      equity           = account.equity,
      size_multiplier  = risk_guard.size_multiplier)

  decisions = DecisionEngine.evaluate_many(inferences, context)
      Sorts by direction.confidence descending, then per symbol runs R0..R9 with
      a context whose open_positions / open_symbols grow as earlier symbols in
      the same batch are approved.

  ---- E. EXECUTION ----------------------------------------------------------
  For each decision, in ranked order:
      if is_executable:
          engine.execute(signal)
              PaperTrader: guard checks -> margin vs free margin -> live entry
                  price -> slippage -> quantity = margin*leverage/fill ->
                  Position.from_signal -> entry fee deducted from the virtual
                  balance -> persist
              LiveExecutor: guard checks -> fetch_account_state ->
                  _resolve_quantity (precision + exchange minimums + margin) ->
                  _preflight (ISOLATED + leverage) -> entry order ->
                  Position.from_signal -> _place_protective_orders (reduce-only
                  TAKE_PROFIT_MARKET + STOP_MARKET on MARK_PRICE) -> on
                  protective-order failure, flatten immediately and REJECT ->
                  persist
          KillSwitchEngaged / QuantSystemError are caught in main._execute.

  ---- F. AUDIT --------------------------------------------------------------
  ALWAYS, for every decision regardless of verdict:
      audit.log_decision(decision, cycle_id, state.value, execution_detail)
        -> AuditRecord flattened -> asyncio.Queue -> the writer task bulk-inserts
           in batches of 64 every 2 s

  ---- POST-CYCLE ------------------------------------------------------------
  _record_equity()
      PaperTrader -> record_equity_point()
      LiveExecutor -> fetch account state, compute drawdown, insert_equity_point
  Log the one-line summary and return the cycle dict.

  ---- CONCURRENTLY, BETWEEN CYCLES ------------------------------------------
  The engine's own monitor task runs every 5 s:
      PaperTrader.mark_to_market: funding accrual -> liquidation check ->
          trailing advance -> stop check -> take-profit check
      LiveExecutor._monitor_loop: excursion update -> trailing advance (cancel
          the old stop, place a new one) -> reconcile every 60 s

4.5 Shutdown sequence
--------------------------------------------------------------------------------

  SIGINT/SIGTERM -> request_shutdown() -> the _shutdown Event fires ->
  asyncio.wait returns -> server.should_exit = True -> finally: shutdown()

    trading_enabled = False
    cancel the setup task and await it
    scheduler.shutdown(wait=False)
    engine.stop()          (monitor cancelled; live also closes the auth client)

5. MACHINE LEARNING SUBSYSTEM

--------------------------------------------------------------------------------
5.1 Overview of the four heads
--------------------------------------------------------------------------------

  #  Head       Class            Question                 Type          Target
  -  ---------  ---------------  -----------------------  ------------  --------------------
  1  Direction  DirectionModel   Where is the market      5-class       label
                                 going?                   classifier    (LabelClass)
  2  Entry      EntryModel       Now, or wait one more    binary        entry_quality
                                 candle?                  classifier    (0/1)
  3  Exit       ExitModel        How should the trade be  3 regressors  target_tp_pct,
                                 managed?                               target_sl_pct,
                                                                        target_trailing_pct
  4  Risk       RiskModel        How much capital and     1 regressor   target_risk_score
                                 leverage?                + rules       ([0,1])

  ARE THERE SEPARATE REGIME AND DECISION MODELS?
    * There is NO regime MODEL in the ML sense. The market regime is a FEATURE,
      produced by the rolling-refit Gaussian HMM in Module B and consumed by all
      four heads as hmm_regime plus four filtered probabilities plus
      hmm_regime_age. It is unsupervised and is refitted inside the feature
      pipeline, not trained or persisted as an artifact.
    * There is NO decision MODEL. The Decision Engine is a deterministic rule
      cascade containing no machine learning whatsoever. It cannot learn, and its
      thresholds come only from DecisionSettings.
    * The Risk model is HALF ML: a regressor produces an opportunity score, and
      hard-coded deterministic arithmetic converts that score plus the direction
      confidence plus the volatility rank into leverage and allocation.

  All four heads consume the SAME 53-column feature matrix. They differ only in
  their target and their estimator type.

--------------------------------------------------------------------------------
5.2 Feature engineering in detail (53 features)
--------------------------------------------------------------------------------

  INPUT: an OHLCV DataFrame (UTC DatetimeIndex, `timestamp` column) plus optional
  futures-metrics and order-book frames.
  MINIMUM: 60 candles, or InsufficientDataError.
  OUTPUT: the input frame plus all 53 columns; warm-up rows carry NaN.

  ---- TREND / DIRECTION (7) -----------------------------------------------
   1 kama_distance         (close - KAMA) / close
   2 kama_slope            KAMA.diff(5) / |KAMA|
   3 kama_slope_fast       KAMA.diff(2) / |KAMA|
   4 ema_fast_slow_spread  (EMA12 - EMA48) / close
   5 close_ema_slow_ratio  close / EMA48 - 1
   6 adx                   Wilder ADX(14)
   7 di_spread             (+DI - -DI) / 100

  ---- STRUCTURE (5) --------------------------------------------------------
   8 fdi                   Fractal Dimension Index over 30 bars, in [1,2]
   9 fdi_trending          1.0 when fdi < 1.5, else 0.0
  10 fdi_delta             fdi.diff(3)
  11 bb_width              (upper - lower) / middle, Bollinger(20, 2)
  12 bb_position           %b, clipped to [-1, 2]

  ---- MOMENTUM (7) ---------------------------------------------------------
  13 rsi                   Wilder RSI(14) / 100
  14 rsi_delta             RSI.diff(3) / 100
  15 log_return_1          log(close).diff(1)
  16 log_return_3          log(close).diff(3)
  17 log_return_12         log(close).diff(12)      - 1 hour
  18 log_return_48         log(close).diff(48)      - 4 hours
  19 momentum_rank         rolling percentile rank of log_return_12 over 288 bars

  ---- VOLATILITY (8) -------------------------------------------------------
  20 atr_pct               ATR(14) / close
  21 atr_rank              rolling percentile rank of atr_pct over 288 bars
  22 realized_vol_12       std of log_return_1 over 12 bars
  23 realized_vol_48       std of log_return_1 over 48 bars
  24 garch_volatility      the ONE-STEP-AHEAD GARCH(1,1) conditional sigma
  25 garch_vol_rank        rolling percentile rank of the above over 288 bars
  26 garch_vol_ratio       garch_volatility / realized_vol_12
  27 vol_of_vol            rolling std of realized_vol_12 over 48, / realized_vol_12

  ---- REGIME (6) -----------------------------------------------------------
  28 hmm_regime            0 BULL / 1 BEAR / 2 HIGH_VOL / 3 SIDEWAYS / -1 UNKNOWN
  29 hmm_prob_bull         filtered probability of the bull regime
  30 hmm_prob_bear
  31 hmm_prob_high_vol
  32 hmm_prob_sideways
  33 hmm_regime_age        consecutive bars in the current regime / 48, capped 5.0

  ---- VOLUME (4) -----------------------------------------------------------
  34 volume_zscore         trailing z-score over 288 bars
  35 volume_rank           rolling percentile rank over 288 bars
  36 volume_trend          mean(volume,12)/mean(volume,96) - 1
  37 dollar_volume_rank    rolling percentile rank of volume*close

  ---- MICRO-STRUCTURE (12) -------------------------------------------------
  38 ob_imbalance          (bid_vol - ask_vol)/(bid_vol + ask_vol), clipped [-1,1]
  39 ob_imbalance_delta    .diff(3)
  40 ob_spread_bps         relative bid/ask spread in bps, floored at 0
  41 ob_spread_rank        rolling percentile rank
  42 funding_rate          the raw recorded rate
  43 funding_rate_delta    .diff(12)
  44 funding_rate_rank     rolling percentile rank
  45 open_interest_change  pct_change(12), clipped [-5,5]
  46 open_interest_rank    rolling percentile rank
  47 long_short_ratio      log(global long/short account ratio)
  48 taker_buy_sell_ratio  log(taker buy/sell ratio)
  49 liquidation_imbalance (liq_buy - liq_sell)/(liq_buy + liq_sell)

  ---- SESSION (4) ----------------------------------------------------------
  50 hour_sin              sin(2*pi*(hour + minute/60)/24)
  51 hour_cos              cos(...)
  52 dow_sin               sin(2*pi*dayofweek/7)
  53 dow_cos               cos(...)

  CAUSALITY MECHANISMS, per feature family:
    * All rolling statistics use trailing windows with min_periods and never
      center=True.
    * GARCH: refitted every 50 bars on a trailing 500-bar window. Between refits
      the variance recursion sigma2_{t+1} = omega + alpha*eps_t^2 + beta*sigma2_t
      rolls forward on realised returns. The value written at t is the forecast
      for t+1, which is by definition known at t.
    * HMM: refitted every 100 bars on a trailing 1000-bar window; regimes come
      from the forward (alpha) filter only. Raw hmmlearn state ids are remapped
      onto the fixed 4-regime taxonomy from the fitted emission means, so the
      feature keeps its meaning across refits.
    * Micro-structure: merge_asof(direction="backward"), so a bar can only see
      snapshots timestamped at or before its own open time.
    * Session features are pure functions of the index.

  DEGRADATION PATHS:
    * arch not installed, or size < window+5, or every fit failed -> the whole
      garch_volatility series becomes an EWMA(span=48) estimate.
    * hmmlearn not installed, or size < window+5 -> regimes are all -1 (UNKNOWN)
      and every probability is 0.25.
    * No order-book / futures frame -> neutral constants (0 imbalance, 0 funding,
      0.5 for every rank), never forward-filled future values.

--------------------------------------------------------------------------------
5.3 Label generation in detail
--------------------------------------------------------------------------------

  For EVERY candle close, the labeler opens a hypothetical LONG and a
  hypothetical SHORT with volatility-scaled triple barriers:

      scale       = ATR_t, else garch_volatility_t * close_t, else close_t*0.0025
      tp_distance = scale * labels.tp_atr_multiple    (default 2.0)
      sl_distance = max(scale * labels.sl_atr_multiple, close*1e-5)  (default 1.0)
      horizon     = labels.max_holding_bars           (default 48 bars = 4 h)

  It then scans forward at most `horizon` candles for the FIRST barrier touch,
  vectorised via sliding_window_view plus running extrema.

  THE THREE PESSIMISM RULES:
    1. When one candle touches BOTH barriers, the STOP is assumed hit first:
           stop_first   = sl_any & (~tp_any | (first_sl <= first_tp))
           target_first = tp_any & ~stop_first
    2. A resolved trade exits exactly at its barrier price. Only an EXPIRED trade
       marks to the horizon close.
    3. Path heat (MAE) is measured and used, not ignored.

  RISK TIER
      mae_ratio = clip(max adverse excursion / sl_distance, 0, 2)
                  0.0 = never went offside; 1.0 = touched the stop
      base tier: <=0.35 LOW, <=0.60 MEDIUM, <=0.85 HIGH, else VERY_HIGH
      volatility escalation, using the entry bar's garch_vol_rank:
          >= 0.95 -> forced to VERY_HIGH
          >= 0.80 -> +1 step, capped at VERY_HIGH
      non-finite MAE -> VERY_HIGH

  SIDE SELECTION
      A side qualifies only if TAKE_PROFIT resolved it.
      Both qualify -> the side that resolved in FEWER bars wins; ties broken by
      the lower mae_ratio.
      Neither qualifies -> NO_TRADE_OR_FAIL, tier NONE.

  THE FIVE CLASSES (LABEL_ORDER - this ordering is the model's class contract)
      0 LONG_SUCCESS_LOW_RISK    long won, tier LOW or MEDIUM
      1 LONG_SUCCESS_HIGH_RISK   long won, tier HIGH
      2 SHORT_SUCCESS_LOW_RISK   short won, tier LOW or MEDIUM
      3 SHORT_SUCCESS_HIGH_RISK  short won, tier HIGH
      4 NO_TRADE_OR_FAIL         neither won, OR the winner was VERY_HIGH and
                                 discard_very_high_risk is set (the default), OR
                                 the row is in the un-simulatable tail

  THE FOUR TARGET FAMILIES
      Direction: `label` (the string) / `label_index` (0..4)
      Entry:     `entry_quality` - 1.0 only when a side was selected AND its
                 mae_ratio <= low_risk_mae_ratio (0.35). This encodes exactly
                 "was this bar a WELL-TIMED entry", not merely "did it win".
      Exit:      target_tp_pct    = (best price in the horizon - entry)/entry*0.9
                 target_sl_pct    = max(heat_to_peak/entry * 1.15,
                                        0.5*sl_dist/entry)
                 target_trailing_pct = target_tp_pct * 0.5
                 All three are NaN when no side was selected.
      Risk:      target_risk_score = (1 - clip(mae_ratio,0,1))
                                     * (0.5 + 0.5*(1 - clip(vol_pct,0,1)))
                 0.0 when no side was selected.

  `label_is_valid` is False for the last `horizon` rows, which cannot be
  simulated. Those rows are dropped by the processor.

--------------------------------------------------------------------------------
5.4 Dataset construction
--------------------------------------------------------------------------------

  Per symbol: features -> labels -> a `symbol` column.
  Pooled: concat, then sort by (timestamp, symbol).
  Cleaning: keep label_is_valid rows; +/-inf -> NaN; dropna over the 53 feature
  columns plus `label` and `target_risk_score`.
  Split into features (53 float columns), direction_target, entry_target,
  exit_targets (3 columns, NaN preserved), risk_target and metadata.

  [DERIVED] Because the dataset is pooled cross-sectionally and sorted by
  timestamp, the chronological split is a genuine OUT-OF-TIME split rather than a
  per-symbol one, exactly as the docstring claims. But it also means the split
  index counts ROWS, not BARS - see 13.5.

--------------------------------------------------------------------------------
5.5 Training pipeline, validation and metrics
--------------------------------------------------------------------------------

  ESTIMATORS
    LightGBM (default): LGBMClassifier / LGBMRegressor.
      n_estimators 400, learning_rate 0.05, max_depth 6, num_leaves 63,
      subsample 0.85 with subsample_freq=1, colsample_bytree 0.85,
      reg_lambda 1.0, min_child_samples 40, random_state 42, verbose -1.
      Classifiers additionally set class_weight="balanced".
    XGBoost (optional): XGBClassifier / XGBRegressor with the equivalent
      parameters and tree_method="hist". NO class weighting.

  VALIDATION
    Time-ordered with a purge gap:
        split_point = int(rows * (1 - 0.2))
        train       = rows [0, split_point - 60)
        validation  = rows [split_point, end)
    The 60 purged rows exist because the labels look forward, so the tail of the
    training block overlaps the validation block's label horizon.
    Early stopping on the validation block, 50 rounds, with a runtime signature
    probe to support both the eval_set and eval_X/eval_y LightGBM APIs.
    The ExitModel computes its own split over its filtered row subset.

  METRICS RECORDED PER HEAD
    Direction: accuracy, balanced_accuracy, log_loss (multi-class, labels 0..4)
    Entry:     precision, recall (zero_division=0), roc_auc (NaN when the
               validation block is single-class)
    Exit:      target_tp_pct_mae, target_sl_pct_mae, target_trailing_pct_mae
    Risk:      mae, r2

  These end up in three places: the head's own metadata (saved inside the
  artifact), the training report returned by train_all, and
  SetupProgress.training_summary, which the panel exposes at
  GET /api/setup/status.

  [NOTE] There is no walk-forward or cross-validated evaluation, no calibration
  check, no feature-importance capture, and no persisted metrics table. The
  metrics live only inside the .joblib artifact and the in-memory progress
  object, both of which are lost when the process restarts.

--------------------------------------------------------------------------------
5.6 Model persistence
--------------------------------------------------------------------------------

  SAVE: joblib.dump(compress=3) of
      {artifact_version: "1.0.0", head: <name>, model: <estimator or dict>,
       feature_columns: [...], metadata: {...}}
  to artifacts/models/<name>.joblib, where <name> is one of direction_model,
  entry_model, exit_model, risk_model. The ExitModel's "model" is a dict of three
  estimators keyed by target name.

  LOAD: load_artifact() never raises. It returns None when the file is missing,
  unreadable, not a dict, or lacks a "model" key. The head then stays unloaded
  and falls back to its heuristic.

  The saved feature_columns list is restored and used by _align at inference, so
  a model trained on a different feature layout still receives its columns in the
  order it expects (with missing ones zero-filled and logged).

  [NOTE] artifact_version is written but never checked on load. A future
  incompatible artifact would be loaded silently.
  [NOTE] joblib.load executes pickle, so an artifact file is executable content.
  The directory is gitignored and locally produced, but any process that can
  write to artifacts/models/ can achieve code execution at the next startup.

--------------------------------------------------------------------------------
5.7 Heuristic fallbacks
--------------------------------------------------------------------------------

  Every head degrades to a documented, deterministic heuristic stamped
  source=HEURISTIC when its artifact is missing.

  Direction: sigmoid(60*kama_slope + 1.2*di_spread +/- 0.25 for a bull/bear HMM
             regime), with the total tradeable mass capped at
             0.45*(0.35 + 0.65*fdi_trending) - i.e. at most 0.45, and only 0.1575
             in a ranging market.
             [DERIVED] The heuristic's maximum long_probability (0.45) is below
             R1's 0.70 threshold, so the direction heuristic ALONE can never
             produce an EXECUTE at default settings.
  Entry:     0.5 plus order-flow alignment (+/-0.15), trending structure
             (+/-0.10) and a spread penalty (+/-0.10); range [0.15, 0.85].
  Exit:      ATR-scaled barriers widened by the volatility rank and the HMM
             regime (x1.35 in HIGH_VOLATILITY, x0.85 in SIDEWAYS).
  Risk:      0.4*confidence + 0.3*(adx/50) + 0.2*fdi_trending
             + 0.1*(1 - garch_vol_rank).

  Rule R9 refuses to let ANY heuristic place a LIVE order. Heuristics ARE
  permitted in paper mode and in backtest mode.
  main.start_trading independently refuses to arm live unless ml.all_loaded.

--------------------------------------------------------------------------------
5.8 How predictions reach a trade
--------------------------------------------------------------------------------

  ModelInferenceResult
      direction.long_probability / short_probability / no_trade_probability
      direction.action, .confidence, .directional_margin, .implied_risk_tier
      entry.probability, .should_enter
      exit_params.take_profit_pct / stop_loss_pct / trailing_activation_pct /
                  trailing_distance_pct / reward_risk_ratio
      risk.leverage / capital_allocation_pct / risk_score / risk_tier / is_abort

  Consumed by the Decision Engine as follows:
      direction.action                 -> R1a
      directional mass                 -> R1b
      directional_margin               -> R2
      no_trade_probability             -> R3
      entry.should_enter               -> R4
      exit_params.reward_risk_ratio    -> R5
      risk.is_abort                    -> R6
      risk.risk_tier                   -> R7
      feature_snapshot["hmm_regime"]   -> R8
      any_fallback + trading_mode      -> R9
      exit_params percentages          -> absolute barrier prices
      risk.leverage / allocation       -> TradeSignal sizing

================================================================================
6. TRADING LOGIC
================================================================================

--------------------------------------------------------------------------------
6.1 Signal generation end to end
--------------------------------------------------------------------------------

  1. The cycle produces one InferencePayload per symbol that passed QC and whose
     newest feature row is fully warmed up and not stale.
  2. Four heads score it.
  3. The Decision Engine ranks symbols by direction.confidence and evaluates each
     through R0..R9 with a running portfolio count.
  4. On a full pass, _build_signal converts percentage geometry into absolute
     prices, applies the Risk Guard size multiplier, and constructs a validated
     TradeSignal. The Pydantic validator re-checks the barrier geometry.
  5. main._execute hands the signal to whichever engine is active.

--------------------------------------------------------------------------------
6.2 LONG / SHORT / NO_TRADE determination
--------------------------------------------------------------------------------

  The direction is NOT read off a single class. Five class probabilities are
  aggregated into three masses:
      long_probability     = P(LONG_SUCCESS_LOW_RISK) + P(LONG_SUCCESS_HIGH_RISK)
      short_probability    = P(SHORT_SUCCESS_LOW_RISK)+ P(SHORT_SUCCESS_HIGH_RISK)
      no_trade_probability = max(0, 1 - long - short)
  action = argmax over those three.

  NO_TRADE arises from FOURTEEN distinct causes, each named in the audit log:
      R0  RED risk guard, operator pause / daily cap, portfolio full,
          symbol already open                                   (verdict BLOCKED)
      R1a direction.action is NO_TRADE
      R1b the directional mass is below 0.70
      R2  |long - short| below 0.15
      R3  the NO_TRADE mass exceeds 0.35
      R4  the entry model says wait
      R5  reward/risk below 1.30
      R6  the risk model returned 0x leverage (volatility veto, confidence veto,
          or a composite too small to round up to 1x)
      R7  the risk tier is not in {LOW, MEDIUM, HIGH}
      R8  the HMM regime is on the block list (empty by default)
      R9  a heuristic fallback in live mode
      R10 the constructed geometry failed TradeSignal validation
  Plus two upstream skips that never reach the engine: the symbol failed QC, or
  its newest feature row is still warming up / stale.

--------------------------------------------------------------------------------
6.3 Confidence definitions
--------------------------------------------------------------------------------

  THREE different "confidence" numbers exist and they are not interchangeable:

  a) DirectionPrediction.confidence
         = max(long_p, short_p, no_trade_p)
         The winning mass overall, which MAY be the NO_TRADE mass.
         Used for: ranking symbols in evaluate_many, and as the
         direction_confidence argument to RiskModel.predict.

  b) directional_confidence (local to DecisionEngine.evaluate)
         = long_p when the action is LONG, short_p when SHORT.
         Used for: the R1 threshold test, the TradeSignal.confidence field, and
         the audit reason string.

  c) DirectionPrediction.directional_margin
         = |long_p - short_p|. The EDGE over the opposing side, tested by R2.
         A 0.72 / 0.71 / ... split passes R1 but fails R2.

  [NOTE] The audit row's direction_confidence column stores (a), while the
  TradeSignal's confidence field stores (b). They differ whenever NO_TRADE is the
  largest single mass.

--------------------------------------------------------------------------------
6.4 Stop loss
--------------------------------------------------------------------------------

  ORIGIN     ExitModel's target_sl_pct regressor, or the ATR-scaled heuristic.
  RAILS      (ml_models._assemble, applied to trained AND heuristic output)
             sl >= atr_pct * 0.5      (when atr_pct > 0)
             sl clamped to [0.0015, 0.0800]  i.e. 0.15% .. 8.00%
  ABSOLUTE   LONG:  stop_loss = price * (1 - sl_pct)
             SHORT: stop_loss = price * (1 + sl_pct)
  VALIDATION TradeSignal rejects a long whose stop is >= the entry price.
  LIVE       A reduce-only STOP_MARKET order with stopPrice on MARK_PRICE,
             placed immediately after the entry fills. If it cannot be placed the
             position is market-closed at once.
  PAPER      Checked every 5 s in mark_to_market, AFTER the liquidation check.
  BACKTEST   Checked per bar against the bar's adverse extreme, and the higher of
             (stop, liquidation) wins for a long.

--------------------------------------------------------------------------------
6.5 Take profit
--------------------------------------------------------------------------------

  ORIGIN     ExitModel's target_tp_pct regressor, or the ATR-scaled heuristic.
  RAILS      tp clamped to [0.0020, 0.1500]
             then clamped to [sl*1.1, sl*6.0]   -> 1.1 <= R:R <= 6.0
             then min(tp, 0.1500)
  ABSOLUTE   LONG:  take_profit = price * (1 + tp_pct)
             SHORT: take_profit = price * (1 - tp_pct)
  GATE       R5 additionally requires reward_risk_ratio >= 1.3.
  LIVE       A reduce-only TAKE_PROFIT_MARKET order on MARK_PRICE.
  PAPER      Checked LAST, after liquidation and stop.
  BACKTEST   Checked only when no adverse level was touched on the same bar.

--------------------------------------------------------------------------------
6.6 Trailing stop
--------------------------------------------------------------------------------

  TWO parameters:
      trailing_activation_pct - where the trail ARMS.
          _assemble clamps it to [tp_pct*0.25, tp_pct*0.95].
          ExitParameters additionally rejects activation > take_profit_pct.
      trailing_distance_pct - how far the stop sits behind price.
          _assemble sets it to clamp(sl_pct*0.6, 0.0015, 0.0800).

  ARMING     Position.should_arm_trailing: price >= trailing_trigger (long) or
             price <= trailing_trigger (short), once only.
  RATCHET    Position.advance_trailing computes
                 candidate = price -/+ price*trailing_distance_pct
             and moves the stop ONLY when the candidate improves. It can never
             loosen.
  EFFECTIVE  Position.effective_stop() returns trailing_stop once armed,
             otherwise stop_loss. Every engine and the dashboard use this.

  PER-ENGINE BEHAVIOUR
    LIVE     _maybe_advance_trailing cancels the existing STOP_MARKET order FIRST
             and then places a new one at the tightened level. "Briefly having no
             stop is safer than briefly having two, which would double-close."
             A failed replacement flattens the position.
    PAPER    advance_trailing is called on every 5 s tick before the stop check.
    BACKTEST Only ratchets when neither pre-existing barrier was touched on the
             bar, and then re-tests the bar's adverse extreme against the
             tightened stop within the same bar.

  [NOTE] The backtester re-anchors trailing_trigger to fill * (1 +/- tp_pct*0.5),
  i.e. always the midpoint of the take-profit distance, discarding the model's
  trailing_activation_pct. The live and paper engines use the model's value.

--------------------------------------------------------------------------------
6.7 Leverage and margin
--------------------------------------------------------------------------------

  SOURCE     RiskModel.predict -> leverage = floor(composite * leverage_cap)
             leverage_cap = min(decision.max_leverage, risk.max_leverage) = 10
  FLOOR      leverage < decision.min_leverage (1) -> ABORT (0x, R6 rejects)
  CAPS       Three independent ceilings, all 10:
               DecisionSettings.max_leverage    (le=10 in the field definition)
               RiskSettings.max_leverage        (le=10)
               TradeSignal.leverage             (ge=1, le=10, schema validation)
             The README's claim that leverage is capped "by schema validation,
             not just by configuration" is accurate: even a hand-crafted
             TradeSignal cannot exceed 10.
  MARGIN MODE Forced to execution.margin_mode ("isolated") before EVERY order via
             set_margin_mode, tolerating Binance's benign "no need to change"
             responses. Leverage is set explicitly before every order too, "because
             a stale 20x leverage from a previous session would silently multiply
             the position size".
  MARGIN     margin_for(equity) = equity * capital_allocation_pct
             notional_for(equity) = margin * leverage
             quantity_for(equity) = notional / reference_price
             The allocation percentage is therefore a MARGIN fraction; leverage
             multiplies it into notional exposure.
  LIQUIDATION long : entry * (1 - 1/leverage + mmr)
              short: entry * (1 + 1/leverage - mmr)
              with mmr = execution.maintenance_margin_rate (0.005).

--------------------------------------------------------------------------------
6.8 Position sizing
--------------------------------------------------------------------------------

  FULL CHAIN, with default settings:

      score       = RiskModel regressor output in [0,1]
      conf_factor = clamp((directional_confidence - 0.70) / 0.30, 0, 1)
      vol_factor  = 1 - garch_vol_rank^2
      tier_factor = LOW 1.0 / MEDIUM 0.75 / HIGH 0.5 / anything else 0.6
      composite   = score * (0.35 + 0.65*conf_factor) * vol_factor * tier_factor

      leverage    = floor(composite * 10)             -> 0 aborts the trade
      allocation  = 0.01 + 0.19 * composite           -> clamped to [0.01, 0.20]

      Then, in DecisionEngine._build_signal:
      allocation  = clamp(allocation * size_multiplier, 0.001, 0.20)
                    where size_multiplier is 1.0 GREEN / 0.4 YELLOW / 0.0 RED

      Finally, at execution time:
      margin      = equity * allocation
      notional    = margin * leverage
      quantity    = notional / entry_price

  EXCHANGE CONSTRAINTS (live only, in _resolve_quantity)
      amount_to_precision rounding
      quantity >= limits.amount.min
      quantity * price >= limits.cost.min
      margin <= equity
  PAPER CONSTRAINT
      margin <= account.free_margin (equity minus committed margin)
  BACKTEST CONSTRAINT
      margin <= equity

  WORKED EXAMPLE (1000 USDT equity, GREEN, score 0.8, confidence 0.85, vol rank
  0.30, tier LOW):
      conf_factor = (0.85-0.70)/0.30 = 0.50
      vol_factor  = 1 - 0.09 = 0.91
      composite   = 0.8 * (0.35 + 0.325) * 0.91 * 1.0 = 0.4914
      leverage    = floor(4.914) = 4
      allocation  = 0.01 + 0.19*0.4914 = 0.1034
      margin      = 103.40 USDT, notional = 413.60 USDT

  [DERIVED] The composite must reach 0.10 for any trade at all. Because it is a
  product of four sub-unit factors, a mediocre score or a high volatility rank
  drives it below the floor and the trade is aborted at R6. This, together with
  R1's 0.70 threshold, is why the system is expected to trade rarely.

--------------------------------------------------------------------------------
6.9 Risk limits and the kill switch
--------------------------------------------------------------------------------

  PER-TRADE
      leverage <= 10 (three independent caps)
      allocation <= 20% of equity as margin
      isolated margin, so the worst case per position is its own margin
      a stop is always placed (live: as a real reduce-only order, or the position
      is flattened)

  PER-PORTFOLIO
      max_concurrent_positions = 5           (R0, enforced across a batch)
      one position per symbol                (R0 + an executor-level check)
      max_daily_trades = 40                  (RiskGuard.can_trade)

  RISK GUARD LADDER
      YELLOW when ANY of:
          daily drawdown >= 3%
          3 consecutive losses
          3 exchange errors within 300 s
        -> size_multiplier 0.4, applied in DecisionEngine._build_signal
      RED when ANY of:
          daily drawdown >= 5%
          peak-to-trough drawdown >= 20%
          5 consecutive losses
          6 exchange errors within 300 s
          the operator presses KILL SWITCH
        -> _trip: latch RED, fan out to every halt callback (emergency_flatten),
           persist to SQLite, refuse all new risk (R0 BLOCKED, and both engines
           raise KillSwitchEngaged from execute()).
      Clearing RED requires POST /api/reset_risk_guard or the panel's RESET GUARD
      button. reset() re-baselines day_start_equity to the current equity so the
      same drawdown does not immediately re-trip, and leaves trading DISARMED.

  BACKTEST does not simulate any of this: DecisionContext is hard-coded to GREEN,
  trading_enabled=True and size_multiplier=1.0.

--------------------------------------------------------------------------------
7.2 Public vs private
--------------------------------------------------------------------------------

  PUBLIC (market-data role, mainnet, NO credentials attached)
      load_markets, fetch_ohlcv, fetch_order_book, fetch_funding_rate,
      fetch_open_interest, fetch_liquidations, fetch_ticker, fetch_tickers,
      the three futures/data ratio endpoints.
      Used by: training, backtesting, paper trading AND live trading.

  PRIVATE (execution role, signed; mainnet or testnet)
      fetch_balance, fetch_positions, fetch_order, create_order, cancel_order,
      cancel_all_orders, set_leverage, set_margin_mode.
      Used by: LiveExecutor only, plus the transient credential-verification
      client built by TradingSystem.verify_credentials.

  Paper trading and backtesting issue ZERO signed requests.

--------------------------------------------------------------------------------
7.3 Market data flow
--------------------------------------------------------------------------------

  Per cycle, per symbol, three concurrent fetches under a semaphore of 8:
      fetch_ohlcv       500 closed 5m candles (the forming bar dropped)
      fetch_order_book  20 levels, reduced to spread / imbalance / microprice
                        over the top 10
      fetch_futures_metrics  a gather of six independently-degrading sub-fetches

  All of it is polling REST. There is no WebSocket usage anywhere in the
  codebase.

  Request-weight controls:
      exchange.enableRateLimit = True (ccxt's own throttle)
      max_concurrent_requests = 8 (two semaphores: one in the fetcher, one in the
      pipeline, both sized from the same setting)
      Universe discovery is exactly two operations regardless of universe size,
      and the ticker call is deliberately unfiltered to keep it one fixed-weight
      request.

--------------------------------------------------------------------------------
7.4 Order execution flow
--------------------------------------------------------------------------------

      TradeSignal
          |
          v
      execute()  --RED?--> raise KillSwitchEngaged
          |      --daily cap / already open?--> rejected ExecutionReport
          v
      _open_position
          |
          +-- fetch_account_state()            (signed)
          +-- _resolve_quantity                (precision + exchange minimums)
          +-- _preflight
          |     set_margin_mode ISOLATED       (signed, non-critical)
          |     set_leverage N                 (signed, critical)
          +-- _place_entry_order
          |     market: create_order(..., reduceOnly False)
          |     limit : create_order + poll fetch_order every 2 s up to 45 s;
          |             on timeout cancel, keep any partial fill, else raise

          +-- _place_protective_orders

          |                   and return a REJECTED report

--------------------------------------------------------------------------------
7.5 Authentication and credential verification
--------------------------------------------------------------------------------

  Credentials come only from EXCHANGE__API_KEY and EXCHANGE__API_SECRET, and are
  attached only to an execution-role ccxt client.
  ccxt handles HMAC-SHA256 signing; options.adjustForTimeDifference = True and
  recvWindow = 10000 guard against clock skew.

  verify_credentials() performs a real signed fetch_balance and translates the
  three failure modes an operator actually hits:
      wrong secret / spot-only key / IP allow-list miss -> one combined message
      clock skew (-1021, timestamp/recvWindow)          -> "Run an NTP sync"
  It never raises and never returns the secret; the key is masked
  ("abcdef...wxyz" or "ab***yz").

  It is invoked from three places:
      POST /api/credentials/verify (the panel's CHECK API KEY button)
      main.start_trading("live") - live is refused when it fails
      LiveExecutor.start() - refuses to start on an invalid key

--------------------------------------------------------------------------------
7.6 Error classification and retry
--------------------------------------------------------------------------------

  TRANSIENT (retried with jittered exponential backoff)
      NetworkError, RequestTimeout, ExchangeNotAvailable, DDoSProtection,
      RateLimitExceeded, OnMaintenance, asyncio.TimeoutError

  PERMANENT (abort immediately - "retrying them only burns the IP weight budget")
      AuthenticationError, PermissionDenied, BadSymbol, ArgumentsRequired
      LiveExecutor additionally treats InsufficientFunds and InvalidOrder as
      permanent.

  Backoff: base 1.0 s, doubling, capped at 60 s, +/-25% jitter, 5 attempts
  (background) or 2 attempts with 0.5-3.0 s delays and a 15 s timeout
  (interactive).

  Every executor failure with critical=True is reported to
  RiskGuard.record_api_error, feeding the 3/6-errors-in-300-s YELLOW/RED ladder.
  Every success calls record_api_success, which CLEARS the window entirely.

  Data-path degradation is layered rather than fatal:
      order book fails       -> None, micro-structure features go neutral
      one futures sub-fetch  -> that field takes its neutral default
      OHLCV fails            -> the symbol is dropped for the cycle
      QC unhealable          -> the symbol is dropped for the cycle
      the whole exchange     -> the panel still starts and says why

--------------------------------------------------------------------------------
7.7 Rate-limit handling
--------------------------------------------------------------------------------

  Four layers:
    1. ccxt's built-in enableRateLimit throttle.
    2. Two asyncio.Semaphores sized from exchange.max_concurrent_requests (8),
       one inside the fetcher (per request) and one inside the pipeline (per
       symbol).
    3. RateLimitExceeded is classified as transient and backs off exponentially,
       and in the executor is additionally reported to the Risk Guard.
    4. Request minimisation by design: universe discovery is two operations
       regardless of universe size; the ticker call is unfiltered on purpose;
       bootstrap fetches only the missing tail; healing re-fetches only the
       damaged window.

  [NOTE] There is no reading of Binance's X-MBX-USED-WEIGHT response headers and
  no global weight budget; back-pressure is purely reactive.

--------------------------------------------------------------------------------
8.4 Authentication model
--------------------------------------------------------------------------------

  A single optional shared secret, WEB__API_TOKEN.
    * BLANK (the default) -> authorise() returns immediately and EVERY endpoint
      is open. The code comments this as "an explicit decision rather than an
      oversight", and the README instructs the operator to firewall the port.
    * SET -> mutating endpoints require the X-API-Token header or a "token" field
      in the JSON body. Read-only endpoints stay open so the dashboard can poll.

  There is no user model, no session, no CSRF token, no rate limiting on the
  endpoints, no CORS configuration, and no TLS.

--------------------------------------------------------------------------------
8.5 Frontend behaviour per page
--------------------------------------------------------------------------------

  DASHBOARD (/)
    Polls /api/status every 5 s, plus /api/audit?limit=25 and /api/logs?limit=120
    inside the same refresh (both wrapped in their own try/catch and treated as
    non-critical).
    Renders: a setup panel (hidden once trading), 8 status cards, a controls row,
    an active-positions table, a health table, a latest-decisions table and a
    live log.
    Button state is driven by setup.can_arm_trading and setup.is_trading, with
    disabled buttons dimmed to 0.4 opacity and given a not-allowed cursor.
    Phase-specific call-to-action text is injected for AWAITING_UNIVERSE,
    SETUP_FAILED and READY.
    Both KILL SWITCH and START TRADING require a window.confirm; the live warning
    reads "START LIVE TRADING WITH REAL FUNDS? Any open paper positions will be
    closed first."

  UNIVERSE (/universe)
    Loads once on page load without a refresh, then only on demand.
    A 45 s AbortController deadline with a per-second elapsed counter, an
    explicit res.ok check before parsing, and an error panel carrying a RETRY
    button plus the "Binance blocks a number of regions and cloud IP ranges"
    diagnosis and the exact curl command.
    Client-side state: ROWS (the full list) and SELECTED (a Set). Filters are
    "eligible only" (checked by default) and a symbol substring search.
    SUGGEST TOP N replaces SELECTED with /api/universe/suggest.
    SAVE & START SETUP confirms, POSTs, and reports the accepted count plus any
    rejections.

  AUDIT (/audit)
    22 columns, symbol and verdict filters, auto-refresh every 15 s, limit taken
    from web.audit_page_size.

  TRADES (/trades)
    14 columns, auto-refresh every 15 s, with a client-side summary of closed
    count, wins, win rate and net USDT.

--------------------------------------------------------------------------------
8.6 How the operator selects symbols / starts / stops trading
--------------------------------------------------------------------------------

  SELECTING SYMBOLS
    1. The system parks in AWAITING_UNIVERSE and the dashboard links to /universe.
    2. The page fetches every active USDT-M perpetual, annotated with price,
       24 h volume, 24 h change, spread, exchange minimum, lot-step cost, max
       leverage, listing age, score and either ELIGIBLE or the specific failure
       reasons.
    3. The operator ticks rows (or presses SUGGEST TOP 30) and presses SAVE.
    4. POST /api/universe/select validates against the live market table, accepts
       ineligible-but-real symbols with a logged warning, persists the selection
       and launches setup with force_retrain set when the selection changed.

  STARTING TRADING
    START PAPER  -> POST /api/trading/start {"mode":"paper"}
    GO LIVE      -> POST /api/trading/start {"mode":"live"}
      Live additionally requires all four trained artifacts and a successful
      signed credential check; the engine switch flattens any open paper
      positions first.
    Nothing trades until one of these is pressed, unless AUTOSTART_PAPER_TRADING
    is true.

  STOPPING
    STOP TRADING -> POST /api/trading/stop {} - stops opening new positions but
      keeps managing open ones to their own TP/SL. Pass {"flatten": true} to
      close them at market instead.
    KILL SWITCH  -> POST /api/kill_switch - trips RED, cancels everything,
      flattens everything, and requires RESET GUARD before trading can resume.

9.2 Table-by-table schema

--------------------------------------------------------------------------------
9.3 Write paths
--------------------------------------------------------------------------------

  Table                  Writer                        Frequency
  ---------------------  ----------------------------  --------------------------
  ohlcv                  DataPipeline (bootstrap and   per backfill and per cycle
                         run_cycle) via upsert_candles
  order_book_snapshots   DataPipeline.run_cycle ONLY   once per symbol per cycle
  futures_metrics        DataPipeline.run_cycle ONLY   once per symbol per cycle
  audit_logs             AuditEngine writer task       batches of <=64 every 2 s
  trades                 Live/Paper executor           on open, then on close
  equity_curve           main._record_equity /         once per cycle
                         PaperTrader.record_equity_point
  system_state           UniverseManager, RiskGuard,   on the relevant event
                         PaperTrader, main._setup_train

  All market-data writes are idempotent upserts, so re-running a cycle or
  replaying a healed block cannot create duplicates.
  Audit writes are batched off the trading loop through a bounded asyncio.Queue
  which DROPS THE OLDEST record under saturation rather than applying
  back-pressure.

--------------------------------------------------------------------------------
9.4 Read paths
--------------------------------------------------------------------------------

  load_ohlcv_dataframe(symbol, limit)   the hot path. Ordered DESC with LIMIT so
      "the last N candles" is an index seek on (symbol, timestamp), then
      re-sorted ascending in pandas.
      Called with limit=1220 per symbol per cycle (inference) and limit=6000 per
      symbol (training/backtest).
  load_futures_metrics_frame(symbol, limit)   7 of the 13 stored columns.
  _load_order_book_frame(symbol, limit)       4 columns, in the processor.
  latest_candle_timestamp / candle_count      aggregates used by bootstrap and
      the setup usability check.
  fetch_audit_logs / fetch_trades             panel reads, id DESC.
  get_state / set_state                       durable key/value.

--------------------------------------------------------------------------------
9.5 Durable key/value state keys
--------------------------------------------------------------------------------

  "universe_selection"  {symbols, updated_ms, updated_by, count}
                        Written by UniverseManager.save_selection; read at every
                        startup and by every one-shot command.
  "trained_universe"    {symbols, trained_ms, rows}
                        Written by main._setup_train; read to decide whether the
                        current artifacts match the current universe.
  "risk_guard_state"    {state, halt_reason, halted_at, day, day_start_equity,
                         peak_equity, current_equity, consecutive_losses,
                         trades_today, realized_pnl_today, updated_ms}
                        This is what makes a RED latch survive a crash-loop.
  "paper_trader_state"  {balance, updated_ms}
                        The virtual balance across restarts.

--------------------------------------------------------------------------------
9.6 Historical data management
--------------------------------------------------------------------------------

  DEPTH      data.history_bootstrap_candles (default 6000 bars ~ 21 days of 5m)
  BACKFILL   Incremental: only the missing tail is requested, computed as
             max(end - 6000 bars, newest_stored + 1 bar). Safe and cheap to
             repeat on every startup.
  GROWTH     The ohlcv table grows without bound; nothing prunes it. 30 symbols
             x 288 bars/day is ~8,640 rows/day, ~3.2 M rows/year.
  RETENTION  purge_audit_logs(older_than_days) exists but is NEVER CALLED. There
             is no scheduled retention job for any table.
  ORDER BOOK / FUTURES HISTORY
             These two tables are populated ONLY by live cycles. bootstrap_history
             writes candles alone. Consequently, on a fresh installation, the
             training dataset's 12 micro-structure features are at their neutral
             defaults for essentially the entire history, and only acquire real
             values for bars observed while the process was running. See 13.5.
  VACUUM     Never run. WAL checkpointing is left to SQLite's defaults.

================================================================================
12. SECURITY ANALYSIS
================================================================================

--------------------------------------------------------------------------------
12.1 API key handling - what is done well
--------------------------------------------------------------------------------

  * Credentials are NEVER attached to the market-data client. _build_exchange
    adds apiKey/secret only when role == "execution". A bug in the data path
    physically cannot reach the account.
  * The secret is never logged, never returned by any endpoint, and never placed
    in an audit row or a trade payload.
  * The key is masked everywhere it is displayed (masked_api_key -> "abcdef...wxyz"
    or "ab***yz" for short keys).
  * verify_credentials builds a SHORT-LIVED authenticated client and closes it in
    a finally block, so the key is not bound to the long-running connection.
  * .gitignore excludes .env and .env.* while whitelisting .env.example.
  * The documentation instructs the operator to disable withdrawals on the key
    and to use an IP allow-list.
  * Live trading is refused until a REAL signed request succeeds, so a spot-only
    key or an allow-list miss is caught before any order is attempted.

--------------------------------------------------------------------------------
12.2 Secrets management
--------------------------------------------------------------------------------

  Secrets live in exactly one place: a plaintext .env file read at process start.
  There is no vault integration, no key rotation, no encryption at rest, and no
  runtime credential injection. The API token for the panel is likewise a
  plaintext value in the same file.

  The .env.example file documents a real parsing hazard that has already caused
  one bug (commit 05f399e): an inline comment after an EMPTY value is parsed as
  the value itself. For WEB__API_TOKEN specifically, this would silently turn
  "no token" into "the token is literally '# my note'", which fails closed
  (nothing would authenticate) rather than open.

--------------------------------------------------------------------------------
12.3 Potential security problems
--------------------------------------------------------------------------------

  P1  THE PANEL IS UNAUTHENTICATED BY DEFAULT AND BINDS 0.0.0.0.
      WEB__API_TOKEN defaults to "" and authorise() returns immediately when it
      is blank. WEB__HOST defaults to 0.0.0.0. On a VPS without a firewall, any
      party who can reach port 8000 can: save an arbitrary universe, trigger a
      retrain, ARM LIVE TRADING, trip the kill switch, and reset the risk guard.
      The code and README both acknowledge this and instruct the operator to
      firewall the port, but the DEFAULT configuration is open.

  P2  NO TRANSPORT SECURITY.
      The panel is plain HTTP by design ("no domain, no reverse proxy, no TLS
      termination required"). The X-API-Token is therefore transmitted in
      cleartext on every mutating request, and the token input on the dashboard
      is a password field whose value crosses the network unencrypted.

  P3  THE TOKEN COMPARISON IS NOT CONSTANT-TIME.
      `if supplied != expected` in web_app.authorise. Over a network this is a
      weak timing oracle, but it is a deviation from standard practice for secret
      comparison.

  P4  READ-ONLY ENDPOINTS ARE NEVER AUTHORISED, EVEN WHEN A TOKEN IS SET.
      /api/status, /api/audit, /api/trades, /api/positions, /api/logs,
      /api/setup/status and all three universe GETs stay open by design so the
      dashboard can poll them. Those endpoints disclose: the masked API key, the
      account balance and equity, every open position with entry/stop/liquidation
      prices, the full decision history, the trade history, and the raw
      application log tail (which includes the startup banner, symbol lists and
      error strings).

  P5  SWAGGER UI IS EXPOSED AT /docs.
      docs_url="/docs" is left enabled, so the complete API surface - including
      every mutating control endpoint - is self-documenting to any visitor.

  P6  NO CORS POLICY, NO CSRF PROTECTION.
      No CORSMiddleware is configured, so browsers apply the default same-origin
      policy to XHR, which mitigates cross-site reads. However the mutating
      endpoints accept simple JSON POSTs and, when no token is configured, have
      no CSRF defence of any kind.

  P7  NO RATE LIMITING ON THE PANEL.
      Nothing throttles requests to /api/*. /api/universe/available with
      refresh=1 forces an upstream Binance call, so an unauthenticated caller can
      drive the process's outbound request weight.

  P8  MODEL ARTIFACTS ARE PICKLES.
      joblib.load executes pickle. Any process able to write to
      artifacts/models/*.joblib achieves arbitrary code execution in the trading
      process at the next startup. load_artifact validates the payload SHAPE
      after unpickling, which is too late to help. artifact_version is written
      but never verified.

  P9  UNESCAPED HTML INTERPOLATION IN THE PAIR PICKER.
      universe_scripts.html builds rows by string concatenation, inserting
      r.symbol into an onchange attribute and (r.reasons) into a title attribute
      without escaping. The values come from the Binance market table rather than
      from operator input, so this is not currently reachable by an attacker, but
      it is unescaped interpolation into the DOM.

  P10 THE API TOKEN CAN BE PASSED IN A JSON BODY.
      authorise() falls back to payload["token"]. That body is not logged by the
      application (access_log is disabled), but it does mean the secret can end
      up in any intermediary that logs request bodies.

  P11 SQL INJECTION - NOT PRESENT.
      Every query is built through SQLAlchemy Core/ORM constructs with bound
      parameters. There is no string-formatted SQL anywhere in the codebase. The
      only raw SQL is the four fixed PRAGMA statements, whose only interpolated
      values are Literal-constrained settings.

  P12 THE KILL SWITCH AND RISK-GUARD RESET ARE SINGLE-FACTOR.
      Both are ordinary POST endpoints behind the same optional shared secret. A
      party holding the token can reset a RED latch that fired for a genuine
      drawdown and immediately re-arm live trading.

13.2 Partially implemented
--------------------------------------------------------------------------------

  1. FUNDING IS NOT CHARGED IN LIVE MODE.
     PaperTrader._accrue_funding and Backtester._accrue_funding both exist.
     LiveExecutor has no equivalent. position.funding_paid is therefore always
     0.0 in live trading, and the realised PnL written to the trades table omits
     funding the exchange did in fact charge. The equity figure is still correct
     because it comes from fetch_balance, but the per-trade attribution is not.

  2. ORDER-BOOK AND FUTURES HISTORY IS NOT BACKFILLED.
     bootstrap_history writes candles only. The order_book_snapshots and
     futures_metrics tables acquire rows exclusively from live cycles. On a fresh
     install the training set's 12 micro-structure features sit at their neutral
     defaults across essentially all 6000 bars.

  3. LIQUIDATION IS NOT DETECTED IN LIVE MODE.
     _book_external_close only distinguishes TAKE_PROFIT from STOP_LOSS/
     TRAILING_STOP by inspecting the two protective orders. An exchange-side
     liquidation is booked as STOP_LOSS at the effective stop price, understating
     the loss.

  4. THE PROCESS POOL PATH IS UNREACHABLE IN PRODUCTION.
     FeatureService supports use_process_pool=True and compute_features_worker is
     written to be picklable, but every construction site uses the default False.

  5. TRAINING METRICS ARE NOT DURABLY STORED.
     They live inside the .joblib metadata and in the in-memory SetupProgress.
     After a restart, GET /api/setup/status reports nothing about the last
     training run.

  6. THE AUDIT PAYLOAD IS WRITTEN BUT NOT READABLE.
     _build_record assembles a rich payload (per-rule checks, model provenance,
     execution detail, model versions) into the JSON column, but
     fetch_audit_logs does not project it, so no API or page can display it.

  7. EQUITY-CURVE DATA IS COLLECTED BUT NOT SURFACED.
     insert_equity_point runs every cycle and fetch_equity_curve exists, but
     nothing calls the reader and no page charts it.

  8. THE BACKTESTER DOES NOT SIMULATE THE RISK GUARD.
     Its DecisionContext is hard-coded to GREEN / enabled / multiplier 1.0, so
     drawdown halts, YELLOW throttling, losing-streak limits and the daily trade
     cap never affect backtest results.

--------------------------------------------------------------------------------
13.5 Risky behaviours found in code
--------------------------------------------------------------------------------

  R1. POTENTIAL DEADLOCK ON A RISK-GUARD TRIP WITH OPEN POSITIONS.
      RiskGuard._trip is always invoked while self._lock is held (from
      update_equity, record_trade_result, record_api_error or
      trigger_kill_switch). _trip awaits every registered halt callback, which is
      an execution engine's emergency_flatten. The trace:

        RiskGuard.update_equity            acquires RiskGuard._lock
          -> _trip(reason)
            -> PaperTrader.emergency_flatten(reason)
              -> close_position(symbol)    acquires PaperTrader._lock
                -> _close(...)
                  -> RiskGuard.record_trade_result(...)
                    -> async with self._lock   <-- ALREADY HELD, not reentrant

      The same shape applies to LiveExecutor.emergency_flatten -> _market_close
      -> _finalise -> record_trade_result, and to any failing ccxt call inside
      that path -> _call -> record_api_error -> the same lock.
      asyncio.Lock is not reentrant, so this awaits forever, on the single event
      loop that also runs the web server and the scheduler.
      It only materialises when at least one position is open at the moment RED
      trips, because emergency_flatten's loop body does not execute otherwise.
      The most likely triggers are the operator's kill switch, a 5% daily
      drawdown, and a 5-loss streak (which fires from inside record_trade_result
      itself, i.e. the lock is already held by the same call chain).

  R2. A RED LATCH FROM A DRAWDOWN BREACH IS NOT PERSISTED WHEN IT FIRES.
      RiskGuard.update_equity returns from INSIDE the `async with self._lock`
      block on both the already-RED path and the fresh-breach path, skipping the
      `await self.persist()` at the end of the method. The RED state is only
      written to SQLite if some later call (record_trade_result, record_api_error,
      trigger_kill_switch, reset) happens to run. A crash between the trip and
      the next persisting call would restart the process in GREEN, defeating the
      latch-survives-a-crash-loop guarantee the module docstring states.
      (Given R1, that later call may never arrive.)

  R3. THE API-ERROR BUDGET IS EFFECTIVELY DISARMED BY record_api_success.
      LiveExecutor._call calls risk.record_api_success() after every successful
      request, and record_api_success CLEARS the entire sliding window rather
      than letting it decay. Reaching api_errors_red (6) therefore requires six
      consecutive failures with no intervening success anywhere in the executor.
      A flapping API - the case the ladder was written for - never accumulates.
      record_api_success also mutates the deque without holding the lock, unlike
      every other mutator.

  R4. THE PAPER TRADER OVER-CHARGES THE BALANCE ON A LIQUIDATION.
      In PaperTrader._close, `net` is clamped to max(net, -margin) for a
      liquidation, but the balance update on the following line adds the
      UNCLAMPED `gross - exit_fee - funding_paid`. When the gross loss exceeds
      the committed isolated margin, the trades table and the virtual balance
      disagree and the balance falls further than isolated margin should allow.
      The subsequent max(_balance, 0.0) only prevents a negative balance.

  R5. THE LABEL PURGE IS MEASURED IN ROWS, NOT BARS.
      ProcessedDataset.train_validation_split purges ml.purge_bars (60) ROWS from
      a POOLED dataset sorted by (timestamp, symbol). With N symbols there are
      roughly N rows per timestamp, so 60 rows is about 60/N bars: with the
      default 30-symbol universe, ~2 bars = 10 minutes. The label horizon is
      max_holding_bars = 48 bars = 4 hours. The purge is therefore roughly 24x
      too small to cover the label lookahead, and training rows whose labels
      resolve inside the validation window survive the split.

  R6. FEATURE-SPACE LEAKAGE ACROSS THE SPLIT IS NOT ADDRESSED.
      Independently of R5, several features have windows far longer than the
      purge: rank_window is 288 bars, hmm_window is 1000 bars and garch_window is
      500 bars. Rolling statistics computed near the boundary draw on bars that
      sit on the other side of it.

  R7. THE CROSS-SECTIONAL POOL IS SPLIT AS ONE SEQUENCE.
      Because all symbols are concatenated and sorted by timestamp, the same
      wall-clock bar appears N times in the dataset. The 20% validation tail is a
      genuine out-of-time block, but rows from the same timestamp and highly
      correlated symbols appear on both sides of the purge gap.

  R8. THE DEFAULT SYMBOL FALLBACK IS NEVER VALIDATED.
      data.symbols (DEFAULT_SYMBOLS) is used verbatim by bootstrap_history,
      build_training_dataset and Backtester.run when no explicit list is passed.
      Unlike UniverseManager.save_selection, nothing checks those symbols against
      the live market table. The list is a static snapshot and includes contracts
      whose ccxt symbol may no longer exist (for example MATIC/USDT:USDT). Those
      symbols would produce BadSymbol errors that the pipeline catches per symbol
      and logs.

  R9. HALT CALLBACKS ACCUMULATE.
      RiskGuard.register_halt_callback appends and there is no unregister.
      main._switch_engine registers the new engine's callback without removing
      the old one, and the startup live-to-paper fallback registers two. After a
      mode switch, a RED trip calls emergency_flatten on a STOPPED engine as well
      as the live one.

  R10. A FAILED MARKET CLOSE LEAVES THE POSITION TRACKED AND UNPROTECTED.
      LiveExecutor._market_close cancels all resting orders on the symbol FIRST,
      then sends the reduce-only market order. If that order fails, the function
      logs CRITICAL and returns a rejected report - but the protective orders are
      already cancelled and the position remains in _positions with no exchange-
      side stop. The monitor loop will keep trailing it, but nothing retries the
      close.

  R11. TRAILING-STOP REPLACEMENT HAS AN UNPROTECTED WINDOW BY DESIGN.
      _maybe_advance_trailing cancels the old stop before placing the new one.
      The docstring justifies this (two stops would double-close), but the
      position is genuinely unprotected between the two calls, and a failure of
      the second call triggers a market close - itself subject to R10.

  R12. THE AUDIT QUEUE SILENTLY DROPS RECORDS UNDER SATURATION.
      _enqueue discards the OLDEST record when the 4000-entry queue is full, and
      only logs on every 100th drop. The drop count is exposed in stats() but not
      in the /api/status health block (which reports queued and written, not
      dropped).

  R13. NO SCHEMA MIGRATION PATH.
      create_all adds missing tables but never alters existing ones. Any future
      column change against an existing quant.db would fail at query time rather
      than at startup.

  R14. UNBOUNDED TABLE GROWTH.
      Nothing prunes ohlcv, audit_logs, equity_curve, order_book_snapshots or
      futures_metrics. purge_audit_logs exists but is never called.

  R15. `_drain` IS RECURSIVE.
      AuditEngine._drain calls itself while the queue is non-empty rather than
      looping. Depth is bounded by queue_size / batch_size (~63), so it is safe
      at the current constants, but it is bounded by configuration rather than by
      construction.

  R16. LIVE MAE/MFE IS COMPUTED FROM POLLED PRICES ONLY.
      LiveExecutor._monitor_loop calls update_excursions(price, price) every 5 s.
      max_adverse_excursion and max_favorable_excursion in the trades table
      therefore reflect a 5-second sample, not true intra-trade extremes. The
      backtester is the only engine that sees genuine bar extremes.

  R17. THE PANEL DEFAULTS ARE OPEN. See section 12.3 P1-P7.

--------------------------------------------------------------------------------
13.6 Inconsistencies between components
--------------------------------------------------------------------------------

  I1. TRAINING FEATURES INCLUDE THE ORDER BOOK; BACKTEST FEATURES DO NOT.
      DatasetProcessor._load_symbol_inputs loads and joins the order-book frame.
      Backtester._prepare passes order_book=None unconditionally. A model fitted
      with real ob_imbalance / ob_spread_bps / ob_spread_rank values is then
      evaluated on rows where those columns are 0, 0 and 0.5. Combined with 13.2
      item 2 (no order-book backfill), the practical effect on a fresh install is
      that both sides are mostly neutral - but they are neutral for different
      reasons and would diverge as live history accumulates.

  I2. THE TRAILING TRIGGER DIFFERS BETWEEN THE BACKTESTER AND THE LIVE/PAPER
      ENGINES.
      Live and paper use signal.trailing_trigger, derived from
      exit_params.trailing_activation_pct (clamped to [tp*0.25, tp*0.95]).
      Backtester._fill re-anchors it to fill * (1 +/- tp_pct * 0.5), always
      exactly half the take-profit distance, discarding the model's prediction.
      The three engines therefore arm trailing at different points for the same
      signal.

  I3. FUNDING TIMING DIFFERS BETWEEN THE PAPER TRADER AND THE BACKTESTER.
      PaperTrader charges every 8 hours measured from the position's open time.
      Backtester charges only on bars whose timestamp is an exact multiple of the
      8-hour interval, i.e. the real 00:00/08:00/16:00 UTC settlements.
      LiveExecutor charges nothing.

  I4. `confidence` MEANS TWO DIFFERENT THINGS.
      DirectionPrediction.confidence is the winning mass overall (possibly the
      NO_TRADE mass) and is what ranks symbols and what RiskModel.predict
      receives. The DecisionEngine's R1 and TradeSignal.confidence use the
      DIRECTIONAL mass. The audit row stores the former under the column name
      direction_confidence.

  I5. implied_risk_tier CANNOT PRODUCE "MEDIUM".
      It returns only "LOW", "HIGH" or "NONE", yet accepted_risk_tiers is
      ("LOW","MEDIUM","HIGH") and RiskModel's tier_factor map has an explicit
      MEDIUM entry (0.75). Whenever risk.risk_tier is empty and the engine falls
      back to direction.implied_risk_tier, "MEDIUM" is unreachable and "NONE"
      fails R7. RiskAllocation.risk_tier is populated from the same
      implied_risk_tier, so the MEDIUM branch of tier_factor is dead code in
      practice; a tier of "NONE" or "UNKNOWN" falls to the 0.6 default.

  I6. THE FEE FALLBACK IS HARD-CODED.
      LiveExecutor._extract_fee estimates price*quantity*0.0005 when the exchange
      reports no fee, rather than reading execution.taker_fee. If an operator
      configures a different taker fee, the estimate does not follow.

  I7. TWO DIFFERENT LOOKBACK CALCULATIONS EXIST.
      DataPipeline.required_lookback_bars() (never called) and
      DatasetProcessor._inference_depth() (used) compute different depths from
      the same settings.

  I8. THE ERROR CLASSIFICATION TUPLES DIFFER BETWEEN THE FETCHER AND THE
      EXECUTOR.
      The executor treats InsufficientFunds and InvalidOrder as permanent; the
      fetcher's PERMANENT tuple does not include them (it includes
      ArgumentsRequired, which the executor's does not).

  I9. THE AUDIT VERDICT COLUMN CARRIES A VALUE THE UI CANNOT FILTER.
      main.py writes verdict="ERROR" for cycle and setup failures. The /audit
      page's dropdown offers only EXECUTE, NO_TRADE and BLOCKED.

  I10. DECLARED-BUT-UNREAD SETTINGS.
      decision.max_positions_per_symbol, risk.require_manual_reset,
      db.pool_size, universe.quote_currency and settings.timezone are all
      defined, documented and validated, but never read by any code path.

  I11. DEFINED-BUT-UNCALLED CODE.
      MarketDataBundle.to_dataframe, DatabaseHandler.load_latest_order_book,
      DatabaseHandler.purge_audit_logs, DatabaseHandler.fetch_equity_curve,
      UniverseManager.clear_selection, UniverseManager.cached_candidates,
      DataPipeline.required_lookback_bars, FeatureEngineer.minimum_rows,
      FeatureService.build_many, MLSubsystem.save_all,
      AuditEngine.log_decisions, core.utils.percentile_rank,
      core.utils.chunked, core.utils.datetime_to_ms, and the exception types
      DecisionEngineError and ConfigurationError.
      Unused enum members: ModelSource.UNAVAILABLE, PositionStatus.FAILED,
      CloseReason.TIMEOUT.
